商业计划书
摘要
粮食节约已上升为国家战略，反食品浪费与食堂精细化管理的政策依据在国家、省两级逐步落地。国家层面，《中华人民共和国反食品浪费法》确立餐饮服务经营者的减损义务，中共中央办公厅、国务院办公厅《粮食节约和反食品浪费行动方案》进一步提出到2027年学校食堂等人均每餐食品浪费量明显下降的目标；省级层面，河北省率先出台国内首部省级专门法规《河北省人民代表大会常务委员会关于厉行节约、反对餐饮浪费的规定》，并印发《河北省政府食安办等五部门关于落实进一步加强校园食品安全工作要求的通知》，推动校园食堂数字化与全过程监管。在此背景下，高校食堂承担集中供餐与食品安全双重责任，客流高度集中于短暂时段、菜品短保、需求又受课程、考试与天气影响，档口长期依赖个人经验判断备餐量，导致“多做会剩、少做会缺”的矛盾突出，食品剩余与经营成本问题在校园场景中尤为典型，亟需可落地、可复盘的精细化管理手段。
本项目以高校食堂档口为研究对象，发现其存在备餐依赖个人经验、闭餐剩余难以处置、经营数据缺失等核心问题；针对上述问题，项目创新性地提出“需求预测引导的分批备餐＋临期限时折扣处置＋连续经营台账”三位一体的食品减损服务方案，通过少量台账记录结合历史销量、星期、天气、校历与活动标记形成需求区间，把经营动作、数据记录与收益核对统一到同一条链路，以降低剩余率、提升售罄率、实现经营收益可量化、可复盘。
基于14个营业日、4类档口、7个菜品共98条经营分析记录，项目完成了指标复算与方法回测。统一口径下，基线期剩余率为13.8%、售罄率为86.2%、MAPE为8.9%；策略期相应指标为6.0%、94.0%和4.5%。结果表明，分批备餐、需求修正与闭餐前处置具有进一步进入档口验证的价值。商业模式由99—199元/月基础订阅、299—599元/月专业服务、管理版本及增量交易3%—5%服务费构成，第一至第三年营业收入预计为1.8万元、11.0万元和35.0万元。可复算的方法链路、轻量化单档口切入方式和明确的食品安全边界，是项目当前的主要亮点。

第一章 服务概述与市场定位
1.1 高校餐饮食品减损场景分析
高校食堂档口每天都需要判断首批做多少、客流变化后是否补餐、临近闭餐是否继续制作，以及预计剩余如何在安全售卖期内处理。高校餐饮具有高频消费、时段集中、成品短保和需求波动四项特征。课程安排、考试周、天气和校园活动经常改变短时流，同一食堂不同档口又存在菜品结构和制作方式差异。
剩余的经济影响并非只是一份餐品售价。成品已经包含食材、调料、能源、包装和人工投入，闭餐后若无法销售，可变成本难以回收；处理与报损还会增加管理成本。反之，若档口为了压低剩余而频繁缺货，则会损失边际收入和学生信任。因此，经营改善应在剩余率、售罄率、缺货风险和毛利之间寻找适合不同菜品的区间。

1.2 目标客户与核心需求识别
档口经营者是首要付费对象，关注备餐建议是否容易执行、是否减少剩余成本、是否增加边际利润，以及记录工作是否占用过多时间。食堂运营方与后勤部门是重要合作方，更关心多档口管理、食品安全、数据授权和反浪费成效。学生是限时优惠的使用者，主要关注价格、餐品状态、取餐位置、截止时间和优惠是否真实。
三类参与者的诉求存在联系，也可能发生冲突。若只提高优惠量，可能侵蚀档口原价销售；若只追求低剩余，可能增加缺货；若为收集报告信息而过多采集，又会增加档口负担和隐私风险。服务设计需要把经营价值、消费体验和管理要求放在同一流程中协调。
1.3 产品服务体系概述
围绕备餐、剩余、限时处置和周期复盘构成轻量经营服务，帮助档口把零散的经营经验沉淀为可记录、可核对的日常方法。服务将经营记录、备餐判断、剩余处置和周期复盘组织成一套可执行的工作方法。档口只需围绕少量核心字段完成日常记录，系统和服务人员再将结果整理成当天能用的建议，降低经营者为了使用工具而额外增加工作的顾虑。
1.4 数字平台功能定位
数字平台承担经营记录、建议展示、优惠发布、预约核销和经营复盘等工作，是服务进入日常经营的工具。档口负责人保留最终确认权，食品安全判断和经营决策责任由档口承担。平台通过分角色信息呈现提高经营效率：档口看到备餐、剩余和风险提醒，学生看到经过确认的优惠信息，运营方看到授权范围内的汇总结果。

第二章 行业环境与政策分析
2.1 高校餐饮行业特征分析
与社会餐饮相比，高校食堂的客流更集中，也更受校历、课程安排、考试周和校园活动影响。档口通常需要在有限时间内完成首批制作、补餐和闭餐处置，传统依靠个人经验的方式在人员更换、菜品增加或客流异常时，往往难以稳定复制。
2.2 反食品浪费政策与校园治理
《中华人民共和国反食品浪费法》明确了餐饮服务经营者在防止食品浪费方面的责任，高校食堂还承担供餐保障、校园治理和育人功能。减损因此不能只停留在宣传层面，而需要建立可记录、可追踪、可复盘的经营机制。对食堂管理者而言，一套能够解释剩余发生在哪些菜品、哪些时段以及采取何种措施的台账，比单次活动更有持续价值。
近年来，高校食堂的信息化建设在支付、消费结算和采购管理等方面逐步完善，但短保餐品的需求判断具有更强的现场性。通用交易数据难以直接转化为备餐动作，由此产生了轻量经营工具与现场陪跑服务的市场空间。
2.3 食堂数字化现状与技术方法参考
公开餐饮需求预测研究普遍表明，历史销量、星期结构、天气、节假日和特殊事件是影响需求的重要变量。移动平均、同星期基线和指数平滑具有数据要求低、解释清晰的优势；树模型能够处理非线性关系与多变量交互，但在数据较少、事件标注不足时不一定稳定。对高校档口而言，方法选择应以持续可用和便于解释为前提。
国内餐饮数字化实践侧重交易、供应链和库存管理，海外食品减损平台则较多采用临期折扣与消费者撮合模式。二者为技术和商业设计提供了参考，但高校食堂具有集中供餐、封闭场景和食品安全责任链等特点，不能直接照搬外卖平台或零售临期模式。
现有研究和实践也揭示了两个关键关系：一是预测准确率需转化为经营收益，建议必须被经营者采纳并进入现场动作；二是剩余下降需同步确认利润改善，避免优惠挤占正常销售或人工交付成本抵消收益。因此后续分析同时考察预测、剩余、采纳、毛利和交付工时。
2.4 行业机会与市场进入条件
目标市场聚焦于短保菜品占比高、备餐和剩余能够计数、经营者愿意配合记录且食品安全责任清晰的档口。先筛选适配场景，再讨论服务价格和复制规模，确保市场规模测算基于实际可得客户。
2.5 政策导向与市场机会关联
政策提供了减损治理的方向，市场提供了高频应用场景，经营者是否愿意持续使用则取决于服务能否带来可感知的收益。三者缺一不可：没有政策与管理支持，合作难以进入；没有经营改善，客户不会付费；没有连续记录，服务也难以形成可信的复盘。
客户意愿和收费能力将在后续合作中通过访谈纪要、付费记录和续费数据分别核
对。

2.6 战略环境综合分析
从政治环境看，《中华人民共和国反食品浪费法》与河北省厉行节约、反对餐饮浪费规定将反浪费纳入经营责任，高校食堂数字化与食品安全监管持续收紧，为可记录、可复盘的减损管理提供了制度激励。从经济环境看，高校餐饮客单价偏低、档口利润较薄，经营者对新增成本高度敏感，服务必须以可核对的收益和较低门槛进入。从社会环境看，学生绿色消费与食品安全意识增强，对透明优惠接受度较高，但对“清库存”式促销同样存在警惕。从技术环境看，移动支付、小程序、需求预测与轻量化经营工具已经成熟，使以少量字段支撑经营决策具备技术可行性（见图2-1）。
从行业竞争结构看：现有竞争者主要是点餐系统、餐饮ERP与优惠平台，其在交易、供应链或流量环节能力较强，但少有面向档口短保菜品减损的专项能力；潜在进入者可能来自通用SaaS向餐饮场景下沉，其威胁取决于能否积累菜品标签、异常规则等现场经验；替代品是档口沿用经验与纸笔记录，成本低但难以复盘；供应商议价能力体现在菜品供应商与云服务价格上，总体影响有限；购买者（档口与运营方）议价能力较强，因其可比较多种工具，倒逼服务以效果举证、按价值收费。
综合优势、劣势、机会与威胁：优势在于校园场景可接近、产品已成型、方法可解释；劣势在于一手经营数据量有限、团队交付资源不足；机会来自反食品浪费政策推动、高校后勤数字化转型与绿色校园建设；威胁来自食堂准入周期长、传统系统可能快速复制简单功能。据此，项目采取“单档口切入、数据驱动经营改善、借助政策窗口进入”的差异化聚焦策略，避免在通用功能上与成熟系统正面竞争。
上述政策、经济、社会和技术因素共同影响高校食堂的经营环境，但档口层面的供需偏差如何在一天中具体发生，需要从经营决策的时间轴进一步观察。
图2-2 一天经营决策与供需偏差形成机制
综合政策导向与经营机制，高校食堂减损的核心不在于技术本身，而在于能否把政策要求转化为档口可执行的动作。下一章将从经营者和学生的具体需求出发，分析服务需要解决的实际问题。
第三章 经营痛点与需求分析
3.1 备餐偏差与剩余成本分析
高峰期间，经营者必须快速决定是否补餐；临近闭餐时，则要在继续销售、及时停止制作和食品安全之间作出判断。备餐过多导致食材与人工成本无法回收，备餐不足又会损失销售并影响学生体验，单纯追求"零剩余"并不符合经营实际。经营改善应在剩余率、售罄率、缺货风险和毛利之间寻找适合不同菜品的区间。
图3-1 档口备餐与分批制作场景
3.2 分时段经营决策与闭餐处置
服务将经营判断拆分为首批备餐、补餐、停止制作和限时处置等具体动作。高峰期的补餐决定是否会缺货，低峰期的停做决定是否会继续扩大剩余，闭餐前的处置则决定已经制作的餐品能否在安全范围内回收部分价值。把这三个节点分开管理，能让档口不再只依靠"当天客流是否充足"来安排生产。
3.3 档口经营者核心痛点
档口经营者真正需要的是当天可执行的建议。相比抽象的预测准确率，他们更关心首批做多少、客流变化后是否补餐、何时停止制作、预计剩余如何在安全时段内销售，以及这些动作最终改善了多少利润。只有建议能够减少试错并形成可见收益，低价订阅才具有持续基础。客流还随校历、考试周、课程表与天气明显波动：开学与期末的备餐量需整体上移或下调，考试周就餐时段前移，分批下课造成客流波峰差异，雨天堂食增加而高温冷餐需求上升。服务需要把这些时间变量并入需求区间与复盘口径，避免同一星期固定模式在特殊时段失灵。
3.4 食堂运营方管理需求
运营方关注的不是某一份餐品卖了多少，而是不同档口是否遵守统一的安全和数据口径，剩余问题是否在可控范围内，异常发生后是否有记录可查。管理端因此应当轻量、汇总、授权明确，避免把档口经营细节变成额外的管理负担。学生端则需要限时优惠具备数量明确、价格透明、截止时间清晰和核销方便等条件。
3.5 学生限时优惠消费偏好
学生端并不需要复杂的经营信息，只需要明确知道餐品是什么、还有多少、优惠是否真实、在哪里取、什么时候失效。只有规则透明、核销简单、餐品状态可信，限时优惠才不会被理解为清库存，而会成为一种更有性价比的就餐选择。
3.6 需求映射与服务动作匹配
档口需要可执行的备餐和复盘动作，运营方需要统一口径与风险提示，学生需要透明且便利的优惠信息。后续产品功能、服务SOP和收费依据，都以这三类需求能否被实际满足为判断标准。

第五章 目标市场与竞争定位
5.1 目标客户筛选条件
早期客户以高校食堂中3—5个标准化菜品的中小档口为主，优先选择高峰集中、闭餐前存在稳定剩余、经营者愿意记录且能够确认成本的场景。运营方版本不在首个档口阶段强行销售，而是在同一食堂出现多个付费档口后，以汇总报告和权限管理形成自然升级。
产品策略遵循最小可用原则。第一阶段提供台账、基础建议、限时优惠和经营复盘，暂不扩展复杂采购、财务和人事功能。每项新增功能都要回答是否减少档口操作、是否改善经营指标、是否降低团队交付工时，避免产品变成大型餐饮系统的缩小复制。
5.2 单档口、单食堂与区域市场测算
市场规模采用自下而上的估算方式。首期聚焦一所高校约20个可服务档口，区域市场按同城10所高校、约200个档口估算，阶段市场按50所高校、约1000个档口估算。长期市场以2919所普通高校为背景，但只有能够触达、愿意记录、具有短保剩余且存在明确付费关系的档口才属于有效市场。

目标客户优先满足三个条件：菜品具有明显短保属性，备餐和剩余能够计数，经营者愿意保持最低限度的连续记录。完全按单制作、成品剩余极少或数据无法记录的档口暂不进入首批市场。首个案例形成后，优先向同一食堂复制，以共享培训、现场沟通和管理报告降低交付成本。
总体战略采用聚焦式进入。早期选择一个剩余问题较明显、菜品标准化程度较高的档口完成诊断与连续使用。首个案例重点核对经营者能否持续记录、建议能否进入动作、收益能否核算以及价格是否具有支付基础。
形成案例后，优先在同一食堂复制。相同管理规则和现场条件可以共享培训、沟通和报告，降低平均交付成本；当同食堂客户密度、续费和贡献毛利达到目标后，再进入同城高校。跨区域扩张需要标准化数据字典、食品安全边界、培训材料和管理版本，不以合作意向代替实际订单。

5.3 现有经营方式与替代方案
经营者经验、纸笔和Excel是最普遍的替代方案，其优势是现金成本低、使用习惯稳定，缺点是难以形成趋势判断和经营动作。传统点餐系统擅长收银与交易，餐饮ERP覆盖采购、库存与财务，外卖和优惠平台拥有流量与支付能力，但这些产品通常不聚焦中小档口的备餐、剩余处置和周期复盘。

5.5 市场定位与竞争壁垒
优势在于校园场景可接近、产品原型已形成、部署成本较低，经营与绿色价值能够同时表达；劣势在于缺少长期一手数据、团队交付资源有限、早期收入规模较小。政策推动反食品浪费和高校经营数字化构成机会，食堂准入周期、传统系统扩展、数据中断和食品安全责任则构成威胁。
基于上述分析，市场定位确定为“面向高校中小档口的轻量化经营减损服务”。项目聚焦备餐、剩余处置和经营复盘，通过经营诊断、工具使用和人工复盘帮助档口降低短保剩余并改善边际利润，同时与食堂现有交易和管理系统协同。
市场规模和定位判断需要经过资料梳理、访谈观察、经营建档、基线记录、策略运行与经营复盘逐步落地，三类资料分别承担不同作用，不能相互替代。

第六章 服务模式与经营流程
6.1 服务流程与经营流程设计
服务流程由经营记录、需求判断、现场执行、限时处置和经营复盘五个环节构成。营业前整理历史销量、备餐和外部事件，系统结合星期、天气与校历输出需求区间；经营者据此决定首批备餐和补餐；临近闭餐时，只对预计剩余且仍处于安全售卖期的餐品发布限量优惠；营业结束后汇总成本、销售、剩余和采纳情况，调整下一周期参数。
流程设计以建议进入经营动作为核心。经营者始终保留最终确认权，遇到临时团购、设备故障、缺货或课程调整时可以标记异常。即使复杂模型没有显著优势，统一台账、分批制作、停止制作提醒和周期复盘仍能创造经营价值。

档口端、学生端和运营管理端共享必要的订单与经营结果，但各自只看到完成工作所需的数据。这样的分工既能减少重复录入，也能把数据授权、食品安全和操作责任落到具体角色。

6.3 备餐决策支持与分批制作
备餐页面给出需求区间、首批数量、补餐参考和停止制作时间。备餐建议输出的是需求区间和行动参考，而不是强制指令。首批制作数量、补餐时点和停止制作提醒可以帮助经营者缩小试错范围，但临时团购、缺货、天气突变等现场情况仍需由档口负责人作最后判断。
6.4 限时优惠机制与安全确认
动态优惠只处理预计剩余部分，发布前由档口确认餐品状态、数量、底价和截止时间。优惠价格不得低于档口确认的毛利护栏，数量不得超过预计剩余，到达截止时间后自动下架。该机制用于降低餐前剩余，不鼓励提前制造折扣预期，也不改变餐品原有保存和销售期限。
档口负责餐品制作、保存、状态确认和最终销售，运营方负责准入与现场监督，团队负责规则配置、页面展示、订单日志和经营建议。任何技术提示都不替代食品安全判断；出现状态异常、超时售卖或投诉时，立即停止相关优惠并保留日志。

6.5 经营复盘与持续改进机制
经营结果在营业结束后回到台账，成为下一周期的调整依据。复盘不仅比较剩余变化，也同时查看售罄、建议采纳、优惠核销和异常原因，避免以单一指标判断服务效果。服务成功需同时满足剩余下降、售罄稳定、毛利不减和持续录入四项条件。

第七章 数字平台与交互设计
7.1 平台功能架构与操作流程
经营记录经表单整理后录入MySQL数据库，Spring Boot负责业务接口、指标计算和权限管理，Thymeleaf完成服务端页面渲染，ECharts用于经营图表展示。该技术组合成熟、维护成本较低，可在低配置服务器上运行，满足产品试用与早期少量档口使用。微信小程序的云函数可作为学生端补充，不要求另购独立服务器。
系统模块包括经营台账、需求判断、备餐建议、限时优惠、订单核销和经营复盘。角色权限、日志、备份和异常提示贯穿各模块。客户数量、并发与数据规模达到实际阈值后，再升级服务器、权限隔离和容灾。

第八章 数据分析与需求预测
8.1 经营建档与数据录入规范
建档阶段明确菜品、售价、单位成本、备餐方式和食品安全边界；营业日记录备餐、售出、剩余、优惠核销和异常情况，营业结束后进行复盘。菜品名称、售价、单位成本、备餐量、售出量、剩余量、日期和异常事件构成最小可用集合；天气、校历和活动标签用于解释波动。字段少一些，才更容易形成连续记录。
8.2 数据处理链路与结果回传
经营工具不是一次性导入数据，而是构成可以持续更新的工作入口。营业前读取历史销售、天气、星期、考试周和活动标记，输出需求区间；营业中由工作人员确认实际备餐、售出和预计剩余，异常客流、临时缺货和设备问题单独标记；营业结束后，实际结果通过数据回传页面写入台账，系统重新计算剩余率、售罄率、预测误差、优惠核销和避免剩余成本。下一周期使用更新后的记录，而不是永远依赖固定数据。
需求判断以可解释的基线方法为起点。数据量少时采用同星期均值、移动平均和人工事件修正；连续记录稳定后，再比较多变量方法是否带来稳定改善。复杂方法只有在误差、经营收益和解释成本三方面优于基线时才继续使用，连续失准则回退到简单基线。

8.3 核心经营指标与计算口径
指标设计同时覆盖模型、经营和商业三类结果。模型层考察MAE和MAPE，经营层考察剩余率、售罄率、优惠核销率和建议采纳率，商业层考察避免剩余成本、增量毛利、交付工时和续费意向。单一指标不能独立证明服务有效，例如剩余率下降可能伴随缺货，核销增加也可能挤占原价销售。

8.4 基线方法与需求预测模型
当前阶段首先建立同星期加权平均或近期移动平均基线，其优点是上线快、解释清楚、少量数据即可运行。增强方法采用LightGBM或XGBoost等树模型，将星期、天气、趋势、校历和事件标签作为输入，处理多变量之间的非线性关系。复杂模型只有在稳定优于基线且维护成本可接受时才进入正式建议。
需求预测输出区间而不是绝对值。系统根据预测区间、菜品制作周期和档口安全量生成首批备餐与补餐参考，并保留人工确认。连续3天误差超过阈值时暂停增强方法，退回同星期基线并验证异常事件、缺货、临时调课和记录错误，防止模型偏差直接放大为经营损失。

8.6 经营复盘、智能摘要与持续迭代
营业结束后，实际售出、剩余、优惠核销和异常情况写入经营台账，系统重新计算核心指标并用于下一周期判断。连续记录稳定后，比较多变量方法是否带来稳定改善；若模型连续失准，则回退到简单基线和人工事件修正。数据反馈形成轻量在线学习机制。 智能经营摘要仅调用后端计算结果和预设模板，帮助经营者识别需求变化、风险菜品和复盘重点；所有经营动作仍由负责人确认。

8.7 数据权限与隐私安全
数据按角色授权。学生只接触优惠和订单信息，档口只查看自身经营数据，运营方在授权范围内查看汇总数据。涉及个人信息、经营成本和食品安全责任的内容均设置最小必要访问范围。学生端使用匿名核销标识，不额外收集姓名、学号和手机号；对外案例经过匿名化和授权，公开数字保留来源索引。
第九章 商业模式与定价设计
9.1 付费对象与客户价值
档口经营者是首要付费方，因为剩余成本、缺货损失和交付效率直接影响其收益。食堂运营方在同一食堂形成多个使用档口后，购买多档口汇总、权限管理、异常报告和协同服务。学校后勤通常不是首期直接付费对象，却决定准入、数据和食品安全边界。学生不承担订阅费用，通过优惠预约形成安全售卖期内的增量交易。
价格必须低于客户能够核对的经营价值。服务首先计算剩余成本减少、优惠回收价值、原价销售变化和额外操作成本，再判断档口获得的收益是否明显高于订阅价格。收益不足时，不以积累数据为由长期收费，而是缩小菜品范围、调整服务或停止收费。形成正向价值后，再讨论续费和同食堂复制。
图9-1 付费协同与价值形成关系
9.2 经营诊断、基础订阅与专业服务
首次合作采用7天经营诊断，交付数据字典、基线记录、问题清单和简版报告，用于判断菜品是否适合、经营者是否能够持续记录以及服务是否存在可见价值。基础订阅适合标准化程度较高的单档口，专业服务增加多菜品参数调整和月度复盘，管理版本面向运营方提供多档口报告和权限管理。
表9-1 服务层级与收入结构
服务升级依据客户价值和人工投入，而不是简单增加功能。档口仅需要日常建议时保持基础版本；菜品波动较大或需要深度复盘时进入专业服务；多个档口需要统一管理时再启用管理版本。这样可以避免小客户为不需要的功能承担成本，也有利于控制团队交付工时。
图9-2 服务交付与收费阶梯
9.3 食堂管理版本与增量交易服务
价格由交付成本、客户价值和支付意愿共同决定。基础订阅覆盖云资源、培训和日常维护，专业服务覆盖参数调整和月度复盘，管理版本按照档口数量和服务范围报价。优惠服务费只针对可追踪增量交易，不对未核销预约收费，也不把学生端流量作为收入。
保守情景下，档口月度价值由减少剩余成本约100元、优惠新增毛利约80元和节省管理时间约50元构成，合计约230元；基准情景下，减少剩余成本约200元、优惠新增毛利约200元和节省管理时间约100元，合计约500元。对应99元和199元订阅，价值价格比约为2.3—2.5倍。实际价格通过真实付款、续费和交付工时校准。
9.4 单档口收益与收费依据
单档口价值不能只用销售额表示。后续获得授权数据后，将以一个匿名档口和3—5个标准化菜品为例，分别计算基线剩余成本、策略期剩余成本、优惠后边际贡献、可能挤占的原价销售、新增操作成本和月服务费。优惠销售额不能全部算作增量利润，只有排除原价销售挤占并扣除相关成本后的部分才计入增量毛利。

第十章 市场推广与客户拓展
10.1 推广策略与渠道
推广以可核对收益而不是功能清单促成付费。早期通过食堂合作准入进入场景，以低门槛诊断服务建立信任；取得案例后，通过档口间口碑、管理方推荐和案例展示进行同食堂复制。跨校拓展以标准化数据字典、培训材料和管理版本为前提。
图10-1 客户转化与续费路径
10.2 客户获取与转化
获客路径为：经营诊断（免费或低成本）→ 基线记录 → 策略运行 → 收益核对 → 付费转化。每个环节设置进入和退出条件，不以注册量代替付费客户。获客成本按有效客户数核算，包含走访、试用物料和案例制作。
10.3 客户留存与续费
续费以年度复盘报告和可核对收益为基础。经营者确认剩余改善、增量毛利和继续使用意向后，才进入续费流程。续费率低于预期时，优先验证建议采纳、交付质量和价格匹配，而非单纯加大推广。

11.1 交付流程与SOP

第十二章 财务预测与资金规划
12.1 财务口径与基本假设
三年预测属于经营情景，不是订单承诺。收入由平均付费档口和年均客单价推算，可变交付成本包括建档、培训、人工复盘、差旅和必要的云资源分摊，固定费用包括产品维护、市场、管理和合规投入。第一年期末付费档口20个，全年平均10个；第二年期末80个，全年平均50个；第三年期末200个，全年平均140个。年均客单价由1800元逐步提高至2500元。
12.2 成本构成与利润推导
成本划分为单档口可变交付、技术基础、开发维护、获客市场和管理合规五类。

第十三章 风险管控与实施规划
13.1 风险识别与处置
高校餐饮风险来自校园准入、后勤流程、寒暑假客流断层、临时活动、食品安全责任和数据授权。风险管理遵循"识别—预防—触发—处置—复盘"：合作前确认授权和责任，营业中设置异常阈值，触发后由人工决定是否调整备餐、暂停优惠或停止相关功能，事后保留记录并修正规则。无法明确食品安全责任、数据授权或现金来源时，优先暂停相关服务。针对校园准入与招标，采取“单档口试点—运营方背书—数据证明价值”的渐进进入路径；针对寒暑假客流断层，采用按次计费与开学前预测校准，避免把季节性停摆简单处理为暂停服务。

食品安全管理遵循档口确认、限时限量、到期下架和日志留存四项原则。平台不销售隔夜或状态不明食品，不以折扣延长保存期限，不替代档口和运营方的现场判断。状态确认、责任核验、发布核验、上架核销和异常处置构成闭环，任何一步不满足条件，都应停止优惠并保留处理记录。

更合理的备餐能够减少食材、能源、包装和处理成本，透明优惠让仍处于安全售卖期的餐品获得销售机会，统一记录帮助运营方了解浪费发生在哪些品类和时段。学生端通过明确数量、位置和截止时间减少无效到店，使反浪费成为可参与的日常行为。管理方可利用匿名汇总观察剩余趋势、数据完整率和异常响应，为档口沟通、食品安全教育和校园治理提供依据。

13.4 阶段实施规划与里程碑
前3个月完成合作准入、访谈问卷、菜品建档、基线记录和首轮策略运行，以产出一份由经营者共同核对的复盘报告为核心目标。第3—6个月在同一食堂复制3—5个档口，检验培训、数据导入和周度复盘能否标准化。第6—12个月根据付费、续费、交付工时和同食堂客户密度决定是否扩展到10个档口或进入第二所高校。
每个阶段都设置进入条件和停止条件。数据连续、收益可核对、经营者愿意付费、食品安全责任明确且贡献毛利为正，才进入下一阶段；任一关键条件长期不成立，则缩小范围、调整服务或暂停扩张。

13.5 总结与未来展望
高校食堂短保餐品剩余并非单一技术问题，而是需求波动、经验决策、信息分散和现场执行共同作用的结果。食刻有数以少量关键数据为入口，把需求判断转化为首批备餐、补餐、停止制作和限时处置，再通过周期复盘连接经营结果，形成兼顾档口利润、学生体验和食堂管理的服务闭环。
经营分析数据支持了数据字段、指标口径和平台流程的复算：14个营业日、98条记录可以贯通经营记录整理、指标计算和图表展示，阶段指标呈现出剩余率与预测误差下降。由于该资料尚不能替代经授权的档口试点，项目将把单位成本、原价销售变化、操作时间、建议采纳和经营者确认纳入下一阶段评估。商业测算表明，业务能否持续经营取决于客单价、交付成本、同食堂客户密度和续费。
已完成公开资料梳理和经营数据分析，随着数据积累，可进一步建立菜品标签、需求区间、异常规则和行业基准，逐步降低新档口建档成本；在客户密度和合规能力成熟后，再探索园区食堂、烘焙和便利店鲜食。未来扩展仍以短保、可计数、可形成经营动作和责任边界清晰为前提。

附录B 档口访谈与现场观察工具
档口访谈采用半结构化方式，沿一个营业日追问事实与决策，不以诱导性问题要求经营者评价项目效果。
1. 基本情况：档口品类、经营年限、营业时段、主要菜品及制作方式。
2. 首批备餐：数量由谁决定，参考哪些历史信息，通常提前多久制作。
3. 营业中补餐：哪些客流或库存信号触发补餐，最小制作批量是多少。
4. 停止制作：临近闭餐何时停做，哪些菜品最容易形成剩余。
5. 剩余处置：现行处理方式、典型数量、可接受的安全售卖截止时间。
6. 数据记录：当前记录方式、可接受字段、每日可投入时间及中断原因。
7. 付费条件：需要看到何种收益、由谁决策、可接受的收费与试用方式。
8. 食品安全与授权：可优惠品类、状态确认人、数据范围和异常处置。

本补充部分用于将原计划书的完整业务内容与当前可运行项目、数据证据和省赛评审要求统一。原正文保留 13 章结构和原有论证深度；本补充只新增当前版本必须明确的定位、数据治理、图表证据、产品边界和评审口径。
一、项目定位升级：从功能集合到经营决策链
本项目的核心不是“有多少页面”或“使用了多少模型”，而是把高校食堂档口的一组连续经营动作连接起来：经营数据采集、需求区间判断、首批备餐、二次补餐、停止制作、剩余登记、安全限时处置、订单核销和经营复盘。评委在阅读时应能回答三个问题：谁在什么时间做什么决定，系统提供了什么证据，结果如何回到下一周期。

八、项目特有的建模与智能体联合调度
食刻有数的智能体不是替代预测模型的“聊天入口”，而是围绕训练模型做独立复核、经营解释和异常提示。系统先由规则引擎与 LightGBM 并行给出需求判断，再将结构化事实包交给智能体生成可读说明；事实包中的数字来自系统字段，受到数字白名单约束，智能体无权修改备餐量、金额、风险等级或最终经营动作。这样既保留模型的可复现性，也让档口负责人能够理解“为什么这样建议”。
图补-6 多源数据—模型—智能体联合调度架构
项目采用“训练模型负责预测、智能体负责旁路复核”的职责分离。智能体没有写入备餐量、价格、风险或食品安全状态的权限；外部大模型 API Key 未配置、调用超时或返回格式异常时，系统仍能够依靠规则引擎、历史区间和模型状态完成确定性校验。该边界是项目可信度的重要组成，而不是对大模型能力的泛化宣传。
九、多源数据体系与数据治理
项目数据按来源、用途和证据强度分层管理。数据流水线遵循“01_raw 原始数据 → 02_processed 处理数据 → 03_output 指标与预测 → src/main/resources/modeling Java运行产物”的路径；每次提交以 DATA_VERSION.json 的哈希清单核对训练文件、特征列和 Java 加载模型的一致性。正式试点前，必须将授权档口新增数据纳入同一字典和版本链路。
现有材料曾出现 SmartBite 合成数据、公开数据集和“全真实、零模拟”等不同表述，也出现不同样本量与指标口径。正式提交时统一以 DATA_VERSION.json、MODEL_CARD.md、数据字典和可复现实验结果为准；未完成统一前，本计划书不把冲突数字写成确定事实，也不以单个 MAPE 数字代替经营改善。
十、从数据到经营建议的可复现链路
建模采用“预训练—校园场景微调—滚动回测—Java导出—运行时复核”的链路。预训练阶段吸收团餐、校园和天气促销数据的共性关系；校园场景微调使用带场景字段的数据；滚动回测按时间顺序逐日预测，避免把未来信息泄漏到训练集；导出后由纯 Java LightGBM 推理，按固定 24 维特征顺序构造输入，并用 Python/Java 结果一致性文件核验。
模型只预测 sold_qty；浪费量、剩余量和经营改善必须分别定义。MAE、WAPE、sMAPE、RMSLE 等指标用于比较预测误差，不能直接解释为“节省了多少食材”或“降低了多少成本”。计划书中的阶段图展示的是当前经营测算样本的变化；真实成效需要新增授权台账、成本与工时记录以及经营者确认后再计算。
