# 食刻有数：一线使用者视角端到端优化方案

更新日期：2026-11-04。对象：高校食堂档口负责人、当班操作人员、食堂/校方数据负责人。本文只把项目当前代码与本地验收作为原型证据；现场接入、经营改善、模型精度、用户采纳和付费续费仍未验证。

## 一、产品目标与使用原则

帮助档口在开餐前形成可核对的备餐计划，营业中及时记录已做、已售和可售余量，闭餐后留下完整结果，让下一餐和周复盘有可信记录。系统给建议与核对，不代替师傅经验、现场盘点、食品安全责任人或学校授权流程。

使用原则：

- 每个数字有日期、餐次、菜品、计量单位、记录状态和来源；不把缺失当作零，也不把营业中盘点当作闭餐结果。
- 建议必须能转成首批、补餐条件和现场确认量；库存、产能、最小批量和准备时间由当班人员核实。
- 原价售出与优惠售出采用包含关系：优惠售出是总售出的一部分。数量关系按同一单位核对，备餐量 = 总售出量 + 当前剩余量；报损、员工餐、转存等若存在，必须另列去向，不能塞入差额。
- 量纲不可混加。当前网页和 Java 经营闭环只支持“份”；“个、公斤、升、锅/批”是后续产品能力，不得让用户选择后仍沿用份模型。
- 刷卡机/POS 只提供交易或核销线索，不能直接观察出锅量和闭餐剩余；即使交易汇总自动化，仍需人工确认菜品映射、退单/套餐拆分、现金单和实际剩余。
- 任何仿真、公开数据与演示数据必须在界面和报告标明其性质，不以校园经营成效宣传。

## 二、当前能力与关键缺口

| 使用环节 | 当前已有能力 | 当前限制/风险 | 优化方向 |
|---|---|---|---|
| 首次准备 | 学校、授权引用、档口、菜品建档；准入检查 | 管理员表单含校方资料和日常操作混在一起；写入不等于授权核验 | 建档设为管理员的一次性任务；授权状态由负责人核验，保留待核验/已核验/已过期及凭据引用 |
| 历史数据接入 | 单条经营记录、CSV 预览导入、来源声明、行级结果、数量校验 | CSV 与旧 POS 字段映射需人工准备；来源声明不是授权证明；错误行不应悄悄跳过 | 提供可下载模板、字段映射预览、重复/缺失/售罄/停业检查、逐行拒绝原因和可重试文件 |
| 营业前计划 | 按菜品、日期、餐次出建议；约束库存、产能、批量、提前期与时段；保存计划并确认采用/调整 | 必须逐菜操作；约束量仍要求份数；选择“全日”不能形成现场执行计划；算法与损失术语占据首屏 | 以“建议总量、首批、何时复核、补餐条件、注意事项”为主；技术依据折叠；校验每项现场条件来源与更新时间 |
| 营业中记录 | 经营页支持部分盘点后再次更新；数量守恒；可关联预测 | 手机逐菜录入负担较大；与刷卡流水未对接；没有明确处理售罄、加菜、停售、转存等事件的单独去向 | 保留人工快录；先做 CSV/只读流水导入，再评估 POS/API；异常事件需原因、时间和操作者 |
| 剩余处置 | 根据盘点生成优惠建议、确认食品安全后发布、已有订单核销 | 优惠建议不自动拥有真实可售库存；核销订单不等价于所有 POS 销售 | 发布前校验盘点时间、剩余量、截止时间与安全确认；优惠售出回写总售出且不重复计数 |
| 闭餐复盘 | 更新同一日期/餐次/菜品记录；看经营摘要、预测/计划/实际拆解 | 当前盘点可能被摘要混入；销售低不能单独证明减少浪费；报损去向字段不足 | 清楚区分“营业中暂记/已闭餐”；复盘同时看剩余、售罄/缺货、报损去向和数据完整度 |
| 单位与称重 | 菜品主数据有单位字段，但当前业务校验为份；离线契约试验含其他单位 | 网页和 Java 接口不支持公斤/升/批次闭环；称重换算不等于销量预测单位 | 分阶段启用单位；无明确换算和成本口径时禁止参与份数预测和跨菜汇总 |
| 权限与异常 | ADMIN、OPERATOR、ANALYST；服务端限制写操作；页面显示加载/错误 | 校方、档口老板、当班人员、复核人责任尚未完全映射；弱网和导入部分失败需加强指引 | 加最小权限矩阵、操作留痕、提交幂等、失败重试、离线草稿提示和数据冲突处理 |

## 三、推荐端到端使用流程

### A. 首次启用（管理员/数据负责人，一次性）

1. 确认学校和档口范围、授权用途、保存期限、负责人和数据来源；授权未核验时明确显示“待核验”，不可用“已接入”措辞。
2. 建立档口、菜品、售卖价格、单位成本、营业餐次与停售信息；确认单位与一份/一批的业务定义。
3. 导入历史经营记录。系统先检查模板字段、日期、餐次、菜品映射、重复行、单位、数值和数量去向；用户逐行确认后再写入。
4. 展示可用于计划的历史覆盖范围、缺失日、售罄日和异常，不以“记录条数多”替代数据可用性判断。
5. 管理员为档口负责人、当班操作人和复核人配置账号/范围；不要求一线人员浏览模型证据或研究报告。

### B. 每餐营业前（档口负责人）

1. 总览明确今天待做事项和最近数据日期；选定具体营业日、早餐/午餐/晚餐及当班档口。
2. 逐菜查看建议总量、首批量、复核时间、可补量范围、售罄/剩余风险和“为何这样建议”的一句话解释。
3. 确认可用原料、共用设备产能、最小批量、备餐提前期、开餐/收餐时间；同一共享资源不可重复分给多个菜品。
4. 系统产生有编号的计划快照；当班负责人采用、调整或自行决定，填写简短原因。建议不自动下发制作命令、扣库存或宣称保证不缺货。
5. 可打印/共享当餐清单；每一行带菜品、单位、首批、总量、复核点和计划编号。

### C. 营业中（当班人员）

1. 只在真实节点更新已制作、正常售出、优惠售出、当前剩余和报损/转存等去向；字段不确定时可暂存，不得默认填零。
2. 若交易系统提供销量，先展示来源及同步时间，由负责人确认菜品映射、撤销/退款、套餐拆分、现金/补录交易处理规则。
3. “售罄、停售、临时加做、原料未到、设备故障”是事件记录，不自动回写成需求真值；由负责人确认是否影响后续建议。
4. 弱网/提交失败时显示未提交草稿和重试状态；重试不得重复生成记录。多人同时修改时提示冲突并保留原值和操作者。

### D. 闭餐、剩余处理和复盘

1. 每菜闭餐清点实物。记录最终制作、总售出、其中优惠售出、剩余，以及报损/转存/员工餐等独立去向；系统逐项校验数量平衡。
2. 优惠发布先选择确认为可售的剩余实物、输入数量、截止时间并由食品安全责任人确认；优惠售出核销后计入总售出一次。
3. 对未售完但不得继续销售的食物明确标记报损，不把转存自动视为下一餐可用库存，除非有安全、保管和批次追溯记录。
4. 闭餐完成后锁定本次结果；修订需说明原因，旧版本可追溯。经营复盘只比较同口径日期/餐次/菜品，分开展示预测偏差、执行偏差、剩余、缺货和记录完整性。
5. 周复盘由负责人核查缺失和异常。没有对照设计时只报告描述性变化，不归因于平台。

## 四、多单位的可落地设计

多单位不是在下拉框里加“公斤/锅”即可。建议单位分三类、分阶段开放：

| 类型 | 示例 | 经营记录建议 | 何时可进入预测 |
|---|---|---|---|
| 离散售卖单位 | 份、个、碗、盒 | 数量可为整数；以实际售卖单位登记 | 同一菜品售卖单位、套餐规则和历史记录稳定后，可独立按该单位建序列 |
| 重量/体积单位 | 克、公斤、毫升、升 | 保存原始值和单位；精度用小数；称重记录带秤/时间/去皮信息 | 先明确预测目标是原料消耗、出品量还是销售量；不得和份数直接合并 |
| 批次单位 | 锅、盆、盘、批 | 保存批次数量，并记录抽样折算系数、适用菜品/容器、有效期和复核人 | 只有持续抽样验证转换稳定且误差达标后，才可映射到标准出品量；否则作为独立记录 |

建议数据契约：每条经营行保存 `quantity_value + unit_code + quantity_dimension + measurement_method`，并可选保存 `conversion_factor + conversion_version + sample_reference`。换算只在同一维度且转换有来源时执行；原始值永不覆盖。人民币成本必须说明按“份/公斤/锅”等哪个基准录入。迁移步骤：先完成菜单和接口单位读写、CSV 模板、报表分组；再开放单一档口试录；最后通过人工抽样与双人复核后启用该单位的建议计算。首阶段继续锁定“份”，在页面明确提示，不用算法输出伪装多单位能力。

## 五、设备和系统接入建议

| 阶段 | 接入方式 | 能解决 | 不能解决/验收条件 |
|---|---|---|---|
| 现在 | 现有 POS/一卡通导出 CSV；人工快录闭餐盘点 | 减少重复抄销量；保留人工确认和审计 | 先核验字段、许可、退款、套餐、现金与菜品编码；不能自动知道制作量和剩余 |
| 试点后 | POS/一卡通只读 API 或定时文件投递 | 自动汇总已核销交易和更新时间 | 不做支付、不替换收银机；接口需学校/供应商授权、幂等、补传和对账 |
| 试点验证中 | 蓝牙/台秤人工称重录入 | 对米饭、汤、称重菜提供原始克/公斤余量 | 校准秤、去皮、容器和抽样换算；称重结果不能直接推断售出份数 |
| 后续可选 | 手机扫码/拍照辅助盘点 | 减少搜索和输入、提供人工确认预填 | 不把图像估计当实测；必须给置信/人工纠正与失败回退 |
| 暂不建议 | 一期摄像头自动数餐、全量微信小程序重做 | 理论上减少人工触点 | 隐私、视角遮挡、套餐识别和维护成本高；没有现场收益证据前不进入主路径 |

刷卡设备保持原有支付用途。食刻有数只接收经授权的最小化汇总字段，不存学生姓名/卡号，不接触支付密钥。接入验收必须有断网补传、日结对账、重复交易去重、撤销退款、菜品映射变更和人工纠错记录。

## 六、角色、异常和兜底

| 角色 | 可做的事 | 关键限制 |
|---|---|---|
| 学校/食堂数据负责人 | 审核授权、数据来源、留存期限、POS 映射与导入批次 | 不默认能查看个人交易身份；负责来源和范围 |
| 档口负责人 | 建立菜品口径、核对现场条件、确认计划、闭餐复核、处理异常 | 计划修改需保留原因；食品安全确认不可由算法替代 |
| 当班操作员 | 查看当餐清单、录入盘点、报告事件、提交草稿 | 限定到所属档口和当班必要数据；不展示实验训练细节 |
| 复盘/分析人员 | 看脱敏汇总、数据完整性和比较结果 | 只读经营数据；区分校园记录、构造验收与公开数据 |
| 系统管理员 | 账号、档口范围、基础配置和审计协助 | 账号权限与业务核验职责分离；敏感变更留痕 |

异常流程必须有明确下一步：无历史数据→只录实际记录并说明建议不可用；历史过旧→提示日期并让负责人决定是否继续；菜品停售/改名→停用旧映射并保留历史；数量不守恒→标出差额字段并阻止“闭餐完成”；导入部分失败→成功行与拒绝行分开，可下载拒绝明细；预测服务不可用→显示最近已确认计划或人工填写，不自动把旧预测当新建议；角色无权→解释联系谁，不展示可点击的写入入口；源数据迟到→保留业务日期、接收时间与修订版本。

## 七、产品改进优先级和验收

### P0：本阶段必须完成

- 日常导航使用“经营者语言”：查看今天、做备餐计划、记录当天经营、处理可售剩余、看经营复盘；首次建档归入“档口与菜品/管理员准备”，不作为日常第 1 步。
- 备餐首屏隐藏 Cu/Co、P5/P95、σ、引擎 ID 和回测统计；在“查看计算依据”中为管理员/分析人员保留来源、截止时间、样本数、方法和局限。
- 计划→当班确认→关联记录→营业中更新→闭餐确认→优惠核销→复盘链路每个环节都展示日期、餐次、菜品、数量单位和状态。
- 复盘将暂记、已闭餐和构造/公开实验分开；不把剩余率下降单独称为改善。
- 当前版本对所有份数业务保持显式单位提示；拒绝非份单位进入预测计划。

验收：档口负责人可不看技术证据完成一餐核心操作；关键字段有即时数量校验；预测计划编号能带入经营记录；优惠售出仅计入总售出一次；重复提交不重复写入；失败后能知道是否保存及下一步。

### P1：本地构造试运行补强

- 建立当班清单式移动页面/打印单、可恢复的未提交草稿、异常事件入口、闭餐状态和多次盘点版本。
- 加入 CSV 模板下载、POS 映射预览与拒绝明细下载；先在隔离构造数据上验收。
- 定义单位字典、数据模型与导入导出契约；先可读/可记非份数据，只有经过验证的单位才能启用对应建议。
- 建立档口、菜品、餐次、操作者权限边界和只读分析视图的真实账号测试。

### P2：获准现场影子运行后

- 仅经书面授权接入 POS/一卡通只读汇总；先并行对账，不自动驱动备餐。
- 做秤重抽样校准、短期用户可用性观察和缺失/修订审计。
- 预注册对照与成本口径后再判断运营成效；是否扩大试点取决于数据完整性、用户负担、售罄/剩余平衡和现场安全审查。

建议验收指标（均为待测目标，不是现有成绩）：关键字段完整率、数量守恒通过率、导入拒绝行可解释率、重复交易识别率、闭餐完成率、每餐额外录入耗时、弱网恢复成功率、单位换算抽样误差、角色越权拦截率。阈值须在试点前由学校和档口负责人共同确定，避免先报喜后定标准。

## 八、项目比赛阶段的证据呈现

当前可展示：页面与 API 的本地构造闭环、已有测试、合成仿真边界分析、公开数据方法验证、来源许可和输入时点审计。必须分别标记“本地构造验收”“合成仿真”“公开数据回测”“校园现场数据”；目前没有校园现场证据。展示模型对比时保留基线优于候选、模型退化等不利结果，同时报告剩余、售罄/缺货与综合损失，不能只挑一个有利指标。

比赛演示脚本建议：管理员建档（说明仅作原型）→导入构造台账并查看错误预览→指定午餐生成计划→人工确认现场库存产能→从计划链接回填营业中盘点→更新闭餐结果与优惠售出→查看描述性复盘和证据范围。旁白明确刷卡机/POS 当前为未来授权接入，不宣称已联机。

## 九、完成定义

用户不需要理解接口、模型名称或数据库术语就能完成一餐；重要数量不会因单位混用、优惠重复计数、营业中与闭餐混淆而失真；数据来源、操作人、修订和异常可追溯；设备掉线或系统不可用时有人工回退；所有校园效果与商业结论均受证据边界约束。未通过授权和现场验收的能力继续标为规划，不把文档设计写成已上线功能。
