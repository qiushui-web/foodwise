# 食堂阿姨便捷录入 × 刷卡机联动 数据采集方案

> 配套项目：食刻有数（FoodWise）高校食堂减损系统
> 原则：**阿姨侧零学习成本、单次录入 ≤10 秒、不改变现有作业流程**；能自动采的绝不人工录。

---

## 一、为什么不能靠阿姨"填表"

| 传统做法 | 现场真实情况 | 后果 |
|---|---|---|
| 纸质表格登记剩餐 | 饭点高峰双手不停、油烟湿手、老花眼 | 漏记、补记、数字拍脑袋 |
| 电脑后台录入 | 档口无电脑、阿姨无账号、系统复杂 | 数据断更，预测模型"无米下炊" |

**核心思路转变：销量数据本来就已经在刷卡机里产生了**——每一笔校园卡/扫码支付都是一条销量记录。阿姨需要人工录入的，只有系统无法自动获取的"闭餐剩余量"这一项。

---

## 二、总体架构：一主两辅三条数据通道

```
┌─────────────────────────────────────────────────────────┐
│                    食刻有数数据中台                        │
│  自动销量聚合 → 特征工程 → LGBM预测 → 明日备餐建议卡        │
└───────────────▲───────────────────▲──────────────▲──────┘
                │                   │              │
      【主通道】刷卡机流水    【辅通道1】小程序录入  【辅通道2】智能秤/拍照
      每笔交易自动入账        仅录"剩余/异常"        剩餐称重/图像估份
      阿姨 0 操作             阿姨每天 ≤3 次点击     进阶学校选配
```

---

## 三、【主通道】刷卡机/一卡通流水自动对接（0 人工录入）

高校食堂消费 90% 以上通过校园一卡通（刷卡/扫码）完成，流水天然包含**档口、时间、金额、商品**四要素。按改造成本分三档落地：

### 档位 1：零改造档——T+1 流水文件投递（推荐先跑通）

- **对接方**：学校一卡通管理中心（信息化建设处/后勤一卡通服务商）。
- **操作**：由一卡通中心每日凌晨自动导出前一日消费流水 CSV，通过 SFTP/企业邮箱/内网共享目录投递到系统服务器。
- **字段需求（最小集）**：
  | 字段 | 示例 | 用途 |
  |---|---|---|
  | 商户号/终端号 | `STALL_03` | 定位档口（映射表维护一次） |
  | 交易时间 | `2026-09-01 11:42:13` | 切分早/午/晚餐次 |
  | 商品编码或商品名 | `hongshao_rou` / 红烧肉套餐 | 聚合到菜品 |
  | 交易金额 | 13.00 | 校验份数（金额÷单价≈份数） |
  | 卡号（脱敏） | `6225****1234` | 仅去重，不留存个人信息 |
- **系统侧**：定时任务每日 02:00 自动拉取 → 清洗 → 按"档口×菜品×餐次"聚合销量 → 写入数据库 → 自动触发模型特征更新。
- **一次性维护**：POS 商品编码 ↔ 系统菜品 ID 映射表（约 30–60 个菜品，半小时维护完，菜品变动时增量维护）。
- **成本**：零硬件投入，仅需后勤一次性授权 + 一个定时脚本。

### 档位 2：API 对接档——准实时自动拉取

- 主流校园一卡通厂商（新开普、正元智慧、迪科远望、宝石卡通等）均提供**商户交易查询接口**。
- 系统每 15 分钟调用一次增量接口，午高峰 12:30 即可看到当日上午实时销量，支持"当天补餐建议"从 T+1 升级为**餐中实时**。
- 需要：一卡通厂商开通接口账号 + 校园内网放行服务器 IP。

### 档位 3：深度档——收银库/串口旁路

- 个别老旧 POS 无 API 时，可在收银机本地部署轻量采集程序，只读同步收银软件数据库（SQLite/MySQL），或旁路打印串口流水，断网续传。
- 属于兜底方案，新校园基本用不到。

> **支付方式覆盖说明**：微信/支付宝个人码收款部分，通过档位 2 的聚合支付商户号流水同样覆盖；纯现金交易（高校占比通常 <5%）由辅通道 1 的小程序"快速报数"补齐。

## 四、【辅通道 1】微信小程序：阿姨每天只点 3 次

为无法自动采集的场景设计（现金单、闭餐剩余量、临时加菜/停售），界面按"老年友好"标准设计：

### 4.1 界面设计原则

- **一屏一任务**：没有菜单嵌套，首页就是本档口今日菜品大卡片；
- **大按钮**：菜品卡片 ≥ 整屏 1/4 高度，字号 ≥18pt，高对比配色；
- **默认值智能**：剩余量默认 0（售罄），销量默认与建议备餐量一致，多数情况下阿姨只需点"确认"；
- **防错**：所有数字二次大字号确认，误触可撤回。

### 4.2 三个高频操作（每个 ≤10 秒）

**① 闭餐报剩余（每天午/晚各一次，核心动作）**

```
┌────────────────────────────┐
│  9月1日 午餐闭餐盘点         │
│                            │
│  ┌──────────────────────┐  │
│  │ 🍖 红烧肉套餐         │  │
│  │  建议备餐 90 · 实售 87 │  │
│  │  剩余 [ 3 ] 份  − ＋  │  │ ← 步进器大按钮，默认0
│  └──────────────────────┘  │
│  ┌──────────────────────┐  │
│  │ 🥬 蒜蓉青菜           │  │
│  │  建议备餐 60 · 实售 60 │  │
│  │  剩余 [ 0 ] 份  − ＋  │  │
│  └──────────────────────┘  │
│                            │
│   [ 🎤 按住语音报数 ]       │ ← "红烧肉剩3份，青菜卖完了"
│   [ ✅ 一键全部售罄并提交 ]  │
└────────────────────────────┘
```

- 语音报数：按住说话 → ASR 转写 → 自动提取菜名+数字 → 高亮让阿姨确认（口音适配：食堂场景词库仅约 50 个菜名，识别率可做到 95%+）；
- "一键全部售罄"：90% 的菜当天卖完，点一下全部置 0 提交。

**② 临时情况一键上报**

四个超大按钮：`停售`（食材没到）、`加菜`（临时增加）、`提前售罄`、`异常备注`（拍照+一句话）。上报后系统自动调整当日预测与明日建议。

**③ 看明日备餐建议（每天收档后推送）**

- 微信服务通知推送："明天午餐建议：红烧肉 85–95 份，首批 70 份，11:30 检查补 15 份"；
- 点开即详情页，阿姨只需点【知道了】，后厨按建议备餐；
- 若现场经验不认可，可拖动调整份数 → 系统记录"人工修正值"，作为后续模型训练样本（人工经验反哺模型）。

### 4.3 拍照估剩（可选增强）

- 对剩余餐盆拍照 → 图像模型估算剩余份数 → 预填数字，阿姨确认即可；
- 适合不方便逐份清点的主食（米饭、馒头按盆估）。

## 五、【辅通道 2】智能称重/视觉（进阶选配）

| 设备 | 采集内容 | 落地方式 |
|---|---|---|
| 备餐智能秤（蓝牙厨用秤 ~150元/台） | 出锅重量 → 按标准份重折算备餐份数 | 小程序蓝牙直连，放锅即录 |
| 剩餐称重台 | 闭餐厨余重量 → 折算浪费克数 | 档口收档时桶放上即称重 |
| 出餐摄像头（AI 视觉） | 打餐动作计数 → 菜品销量 | 顶装摄像头+边缘盒，后期可选 |

建议**不作为一期必需**：主通道（刷卡流水）+ 辅通道 1（小程序）已覆盖 95% 数据需求。

## 六、阿姨一日操作流（落地后）

| 时间 | 动作 | 耗时 | 数据去向 |
|---|---|---|---|
| 08:00 | 看微信推送的今日备餐建议，点【知道了】 | 10 秒 | 记录建议已读 |
| 饭点中 | 正常刷卡出餐，**无任何额外操作** | 0 | 刷卡流水自动入库 |
| 11:30 | 小程序弹窗提醒："已售 70 份，建议补 15 份"（档位2支持） | 看一眼 | — |
| 13:00 闭餐 | 小程序逐菜确认剩余量（多数售罄→一键提交） | 1–2 分钟 | 剩余量入库 → 浪费率核算 |
| 20:00 | 收到明日备餐建议推送 | 10 秒 | 次日备餐依据 |

**阿姨全天与系统交互 < 3 分钟**，且全部在手机微信内完成，不装 App、不记账号（微信授权登录绑定档口）。

## 七、数据安全与隐私

1. **卡号脱敏**：流水仅保留卡序哈希用于去重，不落库任何个人身份信息；
2. **最小权限**：一卡通中心只开放"本食堂商户号"流水，学校侧可审计；
3. **传输安全**：SFTP/HTTPS 加密传输，服务器内网隔离；
4. **数据归属**：经营数据归食堂/后勤所有，系统仅做计算，合同中明确。

## 八、四周落地路线图

| 周次 | 事项 | 负责方 |
|---|---|---|
| 第1周 | 后勤沟通授权；一卡通中心开通 T+1 流水导出；商品编码↔菜品映射表 | 项目组+后勤 |
| 第2周 | 流水自动导入定时任务上线；历史 2–4 周流水回灌，模型冷启动 | 项目组 |
| 第3周 | 小程序"闭餐报剩余+建议推送"上线；2 个档口试点，阿姨现场教学（1 次 15 分钟） | 项目组+档口 |
| 第4周 | 全档口推广；评估数据完整率（目标 ≥95% 销量自动采集）；预测 MAPE 周度复盘 | 全员 |

二期可选项：一卡通 API 准实时对接、智能秤、拍照估剩、视觉计数。

## 九、与现有系统的衔接

- 刷卡流水聚合后的"档口×菜品×日销量"与系统现有预测接口（`/api/predictions/dual`）所需输入完全一致，数据入库即自动进入 LGBM 模型特征管道（滞后销量、7日滚动均值等特征自动更新）；
- 阿姨的人工修正量、闭餐剩余量通过现有经营数据接口入库，同时作为模型再训练样本和浪费率核算依据；
- 数据闭环：**刷卡销量（自动）+ 剩余盘点（半自动）→ 模型预测 → 备餐建议 → 人工确认/修正 → 实际结果回测 → 模型月度再训练**，越用越准。
