# 食刻有数总体产品与技术优化方案

版本：2026-11-09  
适用阶段：竞赛原型、本地构造验收；尚未获得校园现场接入和效果验证  
产品定位：高校食堂中小档口的备餐决策与经营减损服务

## 1. 设计原则与边界

系统围绕档口负责人每餐的实际工作组织：确认经营条件、形成备餐建议、人工确认计划、当班记录、闭餐盘点、合规处置剩余、查看复盘。首页首先回答“今天要处理什么”，其次给出最近有记录营业日的结果，再提供趋势和数据范围。预测建议是人工决策参考，不替代师傅判断、现场盘点、食品安全责任人或学校审批。

配色沿用参考页面的蓝白体系：品牌蓝承担主操作和导航状态，青色用于正常经营量，橙色用于剩余或需注意状态，红色仅用于阻断或高风险。背景使用浅冷蓝灰，内容区域白底，保留参考页的照片横幅和清楚的空间层次。页面圆角以 8–12px 为主，卡片阴影轻量，常规间距采用 8px 基数（8/16/24/32px）；手机端内容边距 16px，桌面端 24–30px。图表按问题选型，不让所有页面重复指标卡加柱状图：走势用堆叠柱，预测用区间带与实际点，流向用分段条，结构占比用横向条，预警用排序清单，复盘用计划/实际对照表。

不得将公开数据、生成数据、原型数据、本地回测写成校园经营成效；不得声称已接通刷卡机、POS 或已验证减损比例。优惠售出是总售出的一部分；所有数量先校验单位与流向平衡。

## 2. 使用者、页面和任务

| 使用者 | 主要目标 | 页面与关键操作 | 结果与下游关联 |
| --- | --- | --- | --- |
| 档口负责人 | 计划并确认每餐制作量 | 经营总览、备餐计划、档口与菜品 | 决策记录生成计划快照，带日期/餐次/菜品/单位进入当班经营记录 |
| 当班人员 | 快速记录制作、销售、余量和去向 | 记录当天经营、经营预警、限时优惠、订单核销 | 暂存或闭餐确认；优惠核销回写总售出一次；异常进入复盘 |
| 校方/项目管理员 | 管理主数据、权限、导入及数据来源 | 首次建档、档口与菜品、数据来源与验证、服务说明 | 维护菜品单位/成本/容量约束，校核导入和数据边界 |
| 复盘/分析人员 | 判断记录质量和经营变化 | 营业快照、需求分析、减损分析、经营复盘、证据页 | 只读分析，比较同口径数据并展示来源、样本和限制 |

### 2.1 推荐导航

1. **今日经营**：经营总览、备餐计划、记录当天经营、处理可售剩余、订单核销、经营预警。
2. **档口准备**：档口与菜品、首次建档、导入规则。
3. **经营分析**：营业快照、需求分析、减损分析、经营复盘。
4. **数据与服务**：数据来源与验证、服务说明、账号与权限。

一线角色默认看到“今日经营”；管理员和分析员获得准备、分析与数据入口。桌面侧栏按分组折叠；手机端维持抽屉导航，打开后聚焦第一项、Esc 关闭并归还焦点。顶部避免重复放置当前页面已有的总览入口。

## 3. 核心业务闭环和耦合关系

```text
档口/菜品/单位/产能
        ↓
经营台账与条件 ──→ 需求建议/解释 ──→ 人工确认 ──→ 备餐计划快照
        ↑                                             ↓
        └── 闭餐结果 ← 当班记录/修订 ← 计划关联 ←──────┘
                         ↓
           余量盘点 → 安全确认 → 限时优惠 → 订单核销
                         ↓                    ↓
                    报损/转存/员工餐/其他去向
                         ↓
       经营复盘、偏差归因、预警、数据证据与模型再评估
```

每一条可写记录都要携带业务日期、餐次、档口、菜品、数量和单位、操作人、状态与来源。计划是不可变的决策快照；后续现场调整生成有原因的修订。台账应区分营业中暂记和闭餐确认。闭餐数量校验按相同单位执行：制作量 = 总售出（其中包含优惠售出） + 报损 + 员工餐 + 转存 + 闭餐剩余；优惠售出只作为总售出中的明细，不重复相加。无称重设备或 POS 时允许人工登记；断网时保留纸面回退和恢复后补录流程。

模块边界：档口与菜品提供主数据；台账是经营事实源；预测只读主数据和已发布台账；计划记录人工采纳及约束；优惠与核销是库存处置子流程；复盘只读已确认版本；预警由台账、计划执行差异和订单状态生成；经营参谋只读以上明确的数据快照并附引用，不直接写库或替用户发布优惠、确认计划、核销订单。

## 4. 多单位和现场硬件落地

每道菜配置基础单位（份/碗/个/千克/升等）、展示精度、可选换算规则及是否允许估算。按件计量以整数校验；称重类允许小数并显示 kg/g；没有可靠换算关系时禁止跨单位求和。称重记录同时保留原始读数、设备/人工来源、记录时间和操作人。批量菜可先录“锅/盆”，但必须配置实测容量换算后才可汇总到 kg 或份。

设备采用渐进接入：当前支持人工录入及Excel、CSV、TSV、JSON文件导入；第二阶段只读导入 POS 销售汇总并做日/餐次对账；第三阶段在学校书面授权后接入一卡通脱敏聚合数据、秤或扫码设备。优先复用现有 POS/秤，不把硬件采购作为产品前置条件。接口失败、设备离线和数据延迟必须显式显示最后同步时间、影响范围和手工回退入口。订单核销码仅用于本平台限时优惠订单，不代表校园支付刷卡。

## 5. 技术栈定位和优化

| 层 | 当前技术 | 清晰职责 | 优化约束 |
| --- | --- | --- | --- |
| 使用界面 | Vue 3、TypeScript、Vue Router、Pinia、Vite | 页面、表单校验、状态提示、图表和角色导航 | 统一 API 客户端/错误状态/格式化；业务域拆分视图组件；图表真实绑定返回数据，不在页面硬编码成效 |
| 业务 API | Java 21、Spring Boot 4、Spring MVC、Validation、Security | 权限、业务规则、事务和 API 契约 | Controller 做输入输出，Service 管业务流程，领域对象守住数量单位和状态转换；接口版本与错误码稳定 |
| 持久化 | Spring JDBC/Data JDBC、Flyway、H2/MySQL | 计划、决策、台账、修订、优惠与核销的可追溯存储 | H2 用于本地演示，MySQL 为部署候选；迁移可前向执行，写操作幂等并记录审计字段 |
| 决策与建模 | Python 建模/回测，Java 运行时推理与规则兜底 | 离线验证、模型包、可复现决策 | 清晰区分训练和运行；模型清单绑定特征/版本/适用范围；缺数据回退透明显示；数据边界变化前禁止在线学习 |
| 经营参谋 | Spring AI 可选适配器 + 确定性规则摘要 | 对建议、偏差和数据限制做自然语言解释 | 只读、受限工具、结构化引用、数字事实校验、超时和无模型降级；不提供自主写操作或设备控制 |
| 验证与交付 | JUnit、Vue typecheck/build、Playwright、Python 测试/报告 | 流程回归、响应式与模型证据复核 | 固定命令、配置、数据快照、指标和截图；本地构造/公开/校园数据分别标识 |

不建议本阶段引入微服务、消息队列、专用向量库或真实设备控制层：现有单校竞赛原型没有吞吐和授权证据支撑这些复杂度。先把模块内接口、数据契约和异步边界设计清楚，待获得现场接入与并发证据后再拆分。

## 6. Agent 定位和安全边界

“经营参谋”定位为**可解释的只读助手**，不把 Agent 包装成自动经营者。输入限定为用户当前选定的档口、菜品、日期、餐次以及被允许读取的台账/预测/复盘快照；输出包含结论、所引用记录或字段、适用日期、缺失信息、限制和下一步人工动作。数值必须来自工具返回结构，不让语言模型计算或补造经营数字。

允许：解释“为何建议此备餐量”、比较方案、指出数据缺口、总结异常、生成待办草稿。禁止：直接保存/修改台账、自动确认备餐计划、改变菜品价格和成本、发布优惠、核销订单、联系校方/供应商、接入支付/一卡通或执行硬件操作。任何未来写操作都必须拆为明确的用户确认表单，由普通业务 API 完成，并记录操作者、输入、确认、幂等键和审计事件。模型故障时回退到规则摘要和原始数据视图。

## 7. 分阶段实施和验收

### P0：本地比赛闭环

- 恢复参考蓝白颜色、照片横幅、蓝/青/橙语义和合适留白；各分析页面分别采用适合问题的图表。
- 首页聚焦待办、最近有记录营业日、近期备餐/售出趋势；每个指标标注日期、单位和数据性质。
- 打通建议→计划→当班记录→闭餐→余量处置→核销→复盘；统一日期、餐次、菜品、单位和状态；保存失败、重复提交、并发修订都有明确反馈。
- 首次建档和数据证据归入管理员/资料区域，避免一线首页出现模型名、接口名、参数缩写和开发任务术语。
- 验收：以本地构造数据完整跑通一餐；计量不混单位；优惠不双计；闭餐可追溯修订；断网时有回退；桌面 1440/1920 与手机 390/768 无溢出，键盘焦点和错误/空/载入状态可用。

### P1：影子试运行准备

- 用空白新档口验证首次建档、多格式数据预览、错误行修订和恢复导入；补齐用户手册与纸面台账模板。
- 建立按菜品/餐次的样本覆盖、区间覆盖率、偏差、缺货与剩余描述指标；与简单基线同口径比较。
- 定义权限、备份恢复、删除/导出请求、脱敏、留存周期和故障值班规则。

### P2：现场授权后

- 先与 POS/一卡通只读汇总并行核对，记录同步延迟、缺失和人工修正，不自动触发生产动作。
- 完成学校、食堂和档口三方的数据授权、隐私告知、食品安全流程确认后，开展限定档口的影子运行。
- 预先规定基线周期、干预周期、对照方式、停止条件和主要指标；只有达到样本与统计条件后才报告效果或商业结论。

## 8. 目录治理与保留规则

根工作区维持五类边界：`项目代码/` 是运行与复现真相；`计划书/`、`PPT/`、`软著资料/` 是正式或申报材料；`数据来源/` 保留来源、许可和原始数据。应用代码按 `src/main/java`（API/业务/领域）、`src/main/resources`（迁移/配置/静态包）、`src/test`、`frontend/src`、`modeling/scripts`、`modeling/tests`、`docs/{product,validation,pilot,competition-validation}` 组织。

清理仅移除可重新生成且未被现行说明、构建、验证或正式稿引用的缓存、临时渲染和重复截图。保留用户截图、比赛材料、现行计划书/PPT、数据来源许可、模型清单、实验配置、测试证据、迁移清单和历史归档包。文件名含“old/archive/backup”或内容重复都不足以单独证明可删除；先检索引用、比较哈希并确认归档清单完整。
