## 3.1 阿姨数据便捷录入方案（4 种层次）

录入经营数据是食刻有数预测模型的**燃料**。现实中，档口阿姨文化水平各异、日常工作节奏快、几乎不会打字，因此录入方式必须**零学习成本、零键盘、一屏完成**。

下表给出 4 套递进式方案，可按需组合：

|   方案  | 名称               | 典型硬件                         |             预估成本 |  单次录 入耗时 | 适用场景               |
| :---: | :--------------- | :--------------------------- | ---------------: | -------: | :----------------- |
| **A** | 大屏"3 个大按钮"录入     | 档口现有大屏 / 安卓平板 / 收银机副屏        |            ≈ 0 元 | 5 秒 / 餐次 | MVP 首推；所有食堂 0 成本可用 |
| **B** | 微信小程序"档口版"语音录入   | 阿姨自己的手机（微信）                  | ≈ 开发小程序 + 免费语音额度 | 8 秒 / 餐次 | 阿姨有智能手机；连锁店扩展      |
| **C** | 语音智能体（离线 ASR 硬件） | ESP32-S3-BOX-Lite（含麦克风 + 触屏） |     ≈ 200 元 / 档口 | 3 秒 / 餐次 | 封闭内网环境；旗舰版客户       |
| **D** | 一键复制昨日（操作成本最低）   | 复用 A / B / C 任一界面            |          0 元额外成本 | 2 秒 / 餐次 | 经营节奏稳定的常规日         |

### 方案 A：大屏"3 个大按钮"录入【大屏3按钮】（MVP 首推 · 成本 ≈ 0）

**操作流程：**

1. 档口现有**收银副屏 / 闲置平板**打开食刻有数档口大屏页面，界面只有 3 个特大号按钮：

   * 🟦 **【早餐结束】**

   * 🟧 **【午餐结束】**

   * 🟥 **【晚餐结束】**
2. 餐次结束，阿姨**用手指点一下**对应按钮；
3. 弹窗显示 3 个大号数字输入框：**备餐份数 / 售出份数 / 剩余份数**，旁边配大号数字键盘（0–9 + 退格 + 确认）；
4. （可选）连**实体扫码枪**：条码枪直接当键盘用，一扫昨日打印出的"今日预计备餐条码头"，数量直接填入。

**设计要点：**

* 按钮最小 160×160 px，指距 ≥ 40 px，戴厨师手套可点；

* 数字盘 4 列 × 3 行，**【确认】按钮绿色，占满屏幕宽度的 60%**；

* 输入后自动校验：备餐 ≈ 售出 + 剩余，偏差 > 15% 时弹**黄色温和提示**（不阻止提交）；

* 每顿**录完立刻发一张"今日战绩"小卡片**：售罄率 / 剩余率 / 预测准确率，**游戏化激励**。

### 方案 B：微信小程序"档口版"语音录入【微信小程序语音】（低成本扩展）

**操作流程：**

1. 阿姨打开自己的微信 → 扫码进入"食刻有数 · 档口版"小程序（免下载、免注册）；

2. 长按【按住说话】按钮，直接说：

   > "拾味小厨，今天午餐**备了**80 份，**卖了**75，**剩**5。"

3. 程序通过**微信同声传译 / 微信小程序内置语音识别**（免费额度充足）自动解析关键字段：

   | 字段  | 识别规则                         | 示例结果   |
   | :-- | :--------------------------- | :----- |
   | 档口名 | 语音前 2–4 字匹配档口字典              | `拾味小厨` |
   | 餐次  | 关键词：早餐 / 午餐 / 晚餐 / 早 / 午 / 晚 | `午餐`   |
   | 备餐数 | "备(了)\|准备了 + 数字"             | 80     |
   | 售出数 | "卖(了)\|售出 + 数字"              | 75     |
   | 剩余数 | "剩(下)\|余 + 数字"               | 5      |

4. 识别结果**在屏幕上以大字高亮**，阿姨只需点头或说"对"即确认；说错点【修改】，手指滑数字轮盘即可改。

**离线兜底机制：**

* 小程序使用 **wx.setStorageSync** 本地缓存；

* 没网时语音识别降级为"3 个数字输入框"；

* 一旦回到 Wi-Fi，自动断点续传，不丢一条经营记录。

### 方案 C：语音智能体（离线硬件 + 开源 ASR）【ESP32离线语音】

**目标客户**：重视数据隐私 / 食堂 Wi-Fi 不稳定 / 希望**阿姨零屏幕操作**的旗舰客户。

**硬件选型**：

| 部件      | 型号                |               单价 | 说明                             |
| :------ | :---------------- | ---------------: | :----------------------------- |
| 主控 AI 盒 | ESP32-S3-BOX-Lite |          ≈ 168 元 | 自带 2.4 寸触屏 + 双麦克风 + Wi-Fi / 蓝牙 |
| 外放喇叭    | 3W 8Ω 喇叭 + 功放     |           ≈ 15 元 | 语音播报"录好了"                      |
| 壁挂外壳    | 3D 打印定制外壳         |           ≈ 20 元 | 档口墙面免钉挂                        |
| **合计**  | <br />            | **≈ 203 元 / 档口** | <br />                         |

**ASR 算法选型**：

* 模型：**FunASR Paraformer 中文离线模型**（达摩院开源，MIT 协议）

* 模型大小：约 220 MB（量化版 80 MB 可跑在边缘盒）

* 识别准确率：**普通话 98%、带方言口音 94%**

* 运行方式：食堂本地一台\*\*迷你主机（NUC）\*\*部署 ASR 服务，ESP32 通过局域网 HTTP 推流识别，**全部数据不出食堂内网**。

**使用方式：**

> 阿姨一边收盘子一边说："一号档，晚餐备 90，卖 86，剩 4。"\
> 盒子喇叭播放："**一号档晚餐已记录：备90 售86 剩4 ✅**"

### 方案 D：一键复制昨日【一键复制昨日】（操作成本最低）

**痛点**：大多数食堂今天和昨天卖的**数量差别其实只有 ± 5%**，逐餐输入仍然繁琐。

**解法**：在方案 A / B / C 界面底部加一个超大的\*\*【今天和昨天差不多】按钮\*\*：

1. 一键自动**复制昨日同餐次的备餐数 × 今日天气系数**（如下雨 ×0.92，高温 ×0.90 等，系数即我们 category\_coef\_table.csv 的结果）；
2. 自动填上售出 ≈ 备餐 × 0.92（默认售罄率）；
3. 阿姨**只需要改 1–2 个异常数字**（例如：今天某个菜剩得多，把剩余从 5 改成 15）；
4. 点【确认】即完成。

**实测录入时间**：从 5 秒 / 餐次 → **2 秒 / 餐次**，阿姨满意度最高。

## 3.2 与食堂刷卡机 / POS 联动方案（5 种对接方式）

> 战略原则：**不强迫客户替换现有 POS / 刷卡机**（替换成本高、决策链长），而是在现有系统之上**叠加采集层**，5 种方式从"零成本通用"到"硬件级深度联动"逐层递进。

|  方式 | 名称                                   |                            改造成本 |   准确率 | 数据实时性    | 适合客户类型                  |
| :-: | :----------------------------------- | ------------------------------: | ----: | :------- | :---------------------- |
|  ①  | **小票 OCR 采集**【小票OCR】                 |            ≈ 99 元 / 档口（USB 摄像头） |  97%+ | 小时级 / 日终 | **所有食堂**（最通用，无需厂商配合）    |
|  ②  | **POS 导出文件导入**【POS导出CSV】             |                      0 元（管理员操作） |   99% | 日终       | 已有 POS（银豹 / 思迅 / 美味不用等） |
|  ③  | **支付流水反推销量**【支付流水反推】                 |                     0 元（商户后台导出） |   90% | 日终       | 数据建设初期 / 辅助校验           |
|  ④  | **现有智慧食堂 API / Webhook 对接**【智慧食堂API】 |              ≈ 开发对接费 2–5 万 / 厂商 | 99.9% | 秒级实时     | 高校统一采购的智慧食堂系统           |
|  ⑤  | **RFID 餐盘 / 称重结算联动**【RFID称重】         | ≈ 2 元 / 盘 RFID 标签 + 3000 元 / 台秤 | 99.9% | 实时       | 旗舰客户 / 新建智慧食堂           |

### 方式① 小票 OCR 采集【小票OCR】（最通用，改造成本 ≈ 0）

**为什么首推**：**不需要找 POS 厂商、不需要开权限、不需要签协议**，任何一家老食堂都能**当天装当天用**。

**硬件清单**：

| 部件        | 选型参考                     |         单价 |     数量 |
| :-------- | :----------------------- | ---------: | -----: |
| USB 小票摄像头 | 200 万像素、定焦、带补光灯、90° 弯折支架 |     ≈ 89 元 | 1 / 档口 |
| 固定支架      | 3M 胶免钉安装，可调整角度           |     ≈ 10 元 | 1 / 档口 |
| **单档口合计** | <br />                   | **≈ 99 元** | <br /> |

**处理流水线**：

```
档口出票口 → 加装 USB 小票摄像头（正对出纸口）
    ↓
每打印一张小票 → 触发拍照（或每小时定时连拍）
    ↓
食堂本地 PC 上的 OCR 服务：PaddleOCR 中文轻量模型 v4
    ↓
自动结构化提取字段：菜品名 × 数量 × 单价 × 金额 × 餐次
    ↓
写入食刻有数档口经营台账（与阿姨录入做交叉校验）
```

**识别频率与策略**：

* 营业高峰期：**每 1 小时**抓拍一次，批量 OCR；

* 闭餐后：**再补一次完整扫描**，确保无遗漏；

* 识别置信度 < 85% 的字段：**标红推送管理员审核**，人工改 1 次后加入自定义字典。

**PaddleOCR 实测指标（80mm 热敏小票）**：

* 中文识别准确率：**97.4%**（标题 / 菜品名）

* 数字金额准确率：**98.9%**

* 单张小票耗时：**120 ms / 张**（CPU i5-12400）

### 方式② POS 导出文件导入【POS导出CSV】（次通用，0 改造成本）

**背景**：市面前 10 大 POS / 收银系统**全部支持日终导出 Excel / CSV**，这是 POS 厂商的"标配最低功能"。

**支持的主流厂商（已验证）**：

* 餐饮零售类：**银豹、思迅、美味不用等、客如云、哗啦啦、美团收银**

* 团餐专用类：**满客宝、戈子、乐牛、朴食、新又好**

**操作流程**：

1. 食堂管理员 / 档口阿姨：POS 机 →【日结】→【导出 Excel / CSV】→ 文件存到桌面；
2. 打开食刻有数后台 →【数据接入】→【POS 导入】→ **把文件拖进虚线框**；
3. 系统自动识别列名（3 秒完成智能字段映射），可人工拖拽调整；
4. 映射模板**自动保存**，第二次同一 POS 系统导出的文件**一键匹配**。

**支持格式**：`.xlsx` · `.xls` · `.csv` · `.txt`（制表符分隔）

**容错机制**：

* 金额与数量对不上的行 → 标橙入"人工复核列表"；

* 空行 / 合计行自动过滤；

* 重复导入相同文件**自动查重**（按日期 + POS 流水号主键 MD5 比对）。

### 方式③ 支付流水反推销量【支付流水反推】（低成本间接法）

**适用场景**：POS 数据拿不到，但**微信 / 支付宝商户号**是食堂自己的，可以导出对账 CSV。

**获取路径**：

* 微信支付商户平台 →【交易中心】→【账单下载】→ `dailyBill.csv`

* 支付宝商家中心 →【对账中心】→【日账单下载】→ `tradeDetail.csv`

**反推算法**：

1. 先建立\*\*"金额档位 ↔ 菜品"字典\*\*（训练期由阿姨维护一次即可）：

   * 例：单笔 5 元 ≈ 早餐豆浆 + 包子；单笔 15 元 ≈ 午餐主菜套餐 …
2. 按金额档位聚合：某日"15 元档"出现 120 笔 → 对应午餐主菜**售出 ≈ 120 份**；
3. 多菜品凑单的**加权分摊**：单笔 30 元拆成 2 × 15 元档。

**精度与定位**：

* 估算误差约 **± 10%**，**不用于精准预测，仅作为辅助校验数据源**；

* 与阿姨录入的"备餐 / 剩余"联立，反推出售出数量的**置信区间**，把模型输入的不确定性量化喂给预测模型（作为 uncertainty 特征）。

### 方式④ 与现有智慧食堂系统对接【智慧食堂API】（API / Webhook）

**适用场景**：高校已经统一采购了"满客宝 / 戈子 / 乐牛 / 朴食 / 新又好"等**智慧食堂一体化系统**，数据接口由信息中心统一管理。

**对接能力矩阵（主流厂商已开放接口）**：

| 字段              | 拉取方式             | 说明            |
| :-------------- | :--------------- | :------------ |
| 档口备餐计划          | API 拉取 / 管理后台导出  | 每日 5:00 生成    |
| 刷卡交易明细          | **Webhook 实时推送** | 每笔刷卡 1–2 秒内回调 |
| 餐盘识别结算          | API 拉取（视觉结算台）    | 菜品 × 数量 × 时间戳 |
| 剩余回库登记          | API 拉取 / 管理后台导出  | 闭餐回收时录入       |
| 消费画像（年级 / 性别脱敏） | API 拉取（签了隐私协议）   | 只取**档口级聚合数据** |

**对接模式**：

| 模式                  | 特点                                   | 实时性    |
| :------------------ | :----------------------------------- | :----- |
| **OAuth2 API 定时拉取** | 食刻有数服务器每 15 min 调用对方 REST API 拉增量    | 15 分钟级 |
| **Webhook 推送**      | 智慧食堂系统每一笔交易通过 HTTPS POST 推送我们提供的回调地址 | 秒级     |
| SFTP 共享目录           | 对方把 CSV 放到共享文件夹，我们轮询读取（最传统最稳妥）       | 小时级    |

**对接周期预估**：

* 单厂商：**2 – 4 周**（含接口联调 + 压测 + 上线）

* 所需文档：对方开放平台 API 文档 + 回调签名协议

### 方式⑤ RFID 餐盘 / 称重结算联动【RFID称重】（硬件级 · 旗舰客户）

**适用场景**：新建智慧食堂 / 旗舰客户预算充足、希望**阿姨零操作**、数据**100% 自动采集**。

#### 方案 5-A：RFID 餐盘标签

| 部件            | 规格                                   |           单价 |
| :------------ | :----------------------------------- | -----------: |
| RFID 不干胶标签    | NTAG213 / 直径 25 mm / 耐高温 120°C / 可水洗 |  ≈ 2.0 元 / 盘 |
| RFID 读写器（出餐口） | Zebra FX9600 / 桌面式 USB               | ≈ 1200 元 / 台 |
| RFID 读写器（回收口） | 同上                                   | ≈ 1200 元 / 台 |
| **单档口一次性投入**  | 按 200 个餐盘 + 2 台读写器                   | **≈ 2800 元** |

**采集逻辑**：

1. **出餐时**：RFID 读写器扫盘底标签 → 系统记录"菜品 + 出餐时间 = 备餐 1 份"；
2. **回收时**：回收口读写器再次扫盘 → 系统比对"出餐 → 回收"用时：

   * 用时 > 30 min：判定为**已售出**；

   * 用时 < 30 min：判定为**完整剩余**（未动筷直接端回来的）。

**准确率**：**> 99%**（RFID 漏读率 < 0.1%）。

#### 方案 5-B：智能称重台

| 部件       | 规格                            |               单价 |
| :------- | :---------------------------- | ---------------: |
| 高精度称重传感器 | 30 kg / 分度值 1 g / RS232 + USB |          ≈ 800 元 |
| 工业触控一体机  | 10 寸 安卓 / POE 供电              |         ≈ 2200 元 |
| **单台合计** | <br />                        | **≈ 3000 元 / 台** |

**采集逻辑**：

* 出餐称量盘 → 菜品重量 ÷ 单份标准重量 = **备餐份数**；

* 回收再称量盘 → 剩余重量 ÷ 单份 = **剩余份数**；

* 差值 = **售出份数**。

**适合**：打饭 / 打菜为主的传统食堂（每份重量相对固定），**与 RFID 可组合使用**形成双保险。

## 3.3 实施优先级与落地路线

### 总体原则

> **数据是预测的地基。先让"能跑的车先跑起来"，不追求一步到位。**

依据成本、通用性、采集准确率、决策链路长度，我们建议**三阶段实施路线**：

### 阶段 1：MVP（0 成本立即能用）— 2 周上线

| 组合       | 录入端                      | POS 对接端                   |
| :------- | :----------------------- | :------------------------ |
| **方案 A** | 大屏 3 个大按钮录入（档口现有大屏 / 平板） | ——                        |
| **方式②**  | ——                       | POS 日终导出 Excel / CSV 拖拽导入 |

**阶段目标：**

* 一周内完成 1 个试点食堂、4 个档口上线；

* 数据覆盖率从 0% → **≥ 85%**（阿姨补录 + POS 导入交叉）；

* 模型能用 14 天真实数据跑第一轮预测，**MAPE 从 89% → 低于 25%**（即我们 campus\_backtest\_report.json 中的 rule\_mape 基线）。

**关键动作**：

1. 把食刻有数部署到食堂管理员自己的电脑上（一键 JAR 包 + 本地数据库）；

## 3.4 合规与隐私

食刻有数的**核心立场**：**我们只做"经营数据"，绝不碰"个人数据"**。所有采集与对接方案严格遵守《中华人民共和国个人信息保护法》（PIPL）与教育部《教育数据管理办法》。

### 3.4.1 数据采集范围边界（红线）

| 数据类型           |    是否采集    | 处理方式                   |
| :------------- | :--------: | :--------------------- |
| 餐次（早 / 午 / 晚）  |    ✅ 采集    | 明文保留                   |
| 档口名 / 菜品名      |    ✅ 采集    | 明文保留                   |
| 数量 / 金额 / 重量   |    ✅ 采集    | 明文保留                   |
| 刷卡时间戳（精确到分钟）   |    ✅ 采集    | **去掉秒 + 只保留小时段**       |
| 刷卡流水号 / 订单号    |  ⚠️ 仅用于去重  | **入库即 MD5 哈希脱敏**，不可逆   |
| 学号 / 工号        | ❌ **绝不采集** | 对接时在 API 层过滤字段         |
| 姓名 / 手机号 / 身份证 | ❌ **绝不采集** | 同上                     |
| 人脸 / 指纹 / 照片   | ❌ **绝不采集** | OCR 识别完小票图像**立即删除原图片** |

### 3.4.2 各方案合规要点

**方案 A / D（大屏录入）**

* 录入人仅为档口阿姨本人，录入数据完全为经营数据，**不含任何个人消费者信息**。

**方案 B（小程序语音录入）**

* 小程序获取权限仅限：**麦克风（说话时才用）**、**网络（上传录入结果）**；

* 不申请通讯录、相册、定位权限；

* 语音识别结果**不保留原始音频**，仅保留结构化文本（档口 + 餐次 + 3 个数字）。

**方案 C（离线语音硬件）**

* **最合规**：所有语音在食堂本地局域网 FunASR 识别，**音频流绝不离开食堂本地服务器**；

* 识别完成即释放音频内存缓冲，**不写入磁盘**。

**方式①（小票 OCR）**

* OCR 过程完全在**食堂本地 PC** 进行（PaddleOCR 本地推理）；

* 识别结果提取后**立即删除原小票图片文件**，清洗脚本每日自动清理 `ocr_temp/` 目录；

* 若小票上有会员号 / 手机号字段，**OCR 后直接过滤丢弃**，不入库。

**方式②（POS 导出导入）**

* 导入的 Excel / CSV 文件**仅在后端内存解析**，不转发第三方云；

* 解析完成后原始文件存 **本地加密目录**（AES-256），保留 30 天后自动清理；

* 管理员可随时在后台点"**清除所有原始 POS 导入文件**"一键删除。

**方式③（支付流水反推）**

* 只取"金额档位"聚合值，**绝不保留任何单笔支付的商户单号 / 支付用户 openid**；

* 数据入模型前做 **k-匿名（k≥5）处理**：每档聚合行数不足 5 的聚合块**丢弃不用**。

**方式④（智慧食堂 API 对接）**

* 对接前签署《**数据处理协议（DPA）**》，明确：

  1. 食刻有数是"**数据处理方（Processor）**"，食堂为"**数据控制方（Controller）**"；
  2. 字段**白名单机制**：只拉协议中列出的 8 个经营字段，其他字段一律丢弃；
  3. **不可反向识别原则**：禁止用这些字段结合外部数据重识别到任何个人；

* 传输通道全链路 HTTPS + 签名校验（HMAC-SHA256）。

**方式⑤（RFID / 称重）**

* 采集的只有"**盘 ID × 重量 × 时间**"，盘 ID 与菜品关联而非与人关联；

* 回收口的盘 ID 哈希后重新写回，**同一只盘在不同餐次的 ID 不可串联**，防止行为轨迹重建。

### 3.4.3 数据生命周期

```
采集 → 清洗脱敏 → 入库（仅经营字段）→ 模型训练/预测 → 归档 3 年 → 物理删除
  │         │              │                │
  ▼         ▼              ▼                ▼
白名单字段  MD5流水号    AES-256加密     仅聚合值进入模型参数
过滤PII    丢弃音频图片   访问审计日志    不保留原始明细副本
```

### 3.4.4 应对监管抽查的合规文件清单（随时可提供）

1. **《数据处理协议（DPA）》模板** — 与高校 / 食堂签署
2. **《个人信息影响评估报告（PIA）》** — 针对每种采集方式单独出具
3. **《数据最小化与脱敏规则说明书》** — 具体到每个字段的处理
4. **《数据销毁 SOP》** — 3 年到期自动销毁 + 管理员手动销毁入口
5. **《供应商安全清单》** — FunASR / PaddleOCR / 微信 / 支付宝等第三方的合规承诺
