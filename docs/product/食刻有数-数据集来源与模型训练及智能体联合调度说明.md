# 食刻有数 · 数据集来源、模型训练与智能体联合调度说明

> 口径说明：原始公开数据与来源按可追溯方式记录；项目内经营流程台账另行标注为 `simulation`，不作为真实校园试点成效。

> 本文档回答四个问题：**数据从哪来（具体路径与调研来源）→ 数据在项目里干什么 → 模型怎么训练 → 训练好的模型如何与智能体结合、嵌入系统联合调度**。
>
> 数据治理原则：原始观测、统计派生、模型预测和流程仿真分层标注。公开数据集按来源、许可、时间范围和文件版本记录；项目内 14 天经营台账用于流程与回测管线验证，不能替代经授权的河北现场数据。

## 一、数据集具体路径与调研来源

## 二、各数据集在本项目中的作用

| 数据集                       | 在项目中的角色            | 具体作用                                                                                             |
| ------------------------- | ------------------ | ------------------------------------------------------------------------------------------------ |
| ① `university_food_waste` | **微调底座 + 效果验证核心**  | 训练最终上线的 LGBM 高校模型（2600 行）；滚动回测得出 MAPE 3.867%；`waste_rate`/`Cost_Loss` 字段是界面"减损金额、CO₂、节水"指标的真实来源  |
| ② `gylaf_campus`          | **预训练增量 + 损耗率校准源** | 提供中国高校真实销量—天气规律进入预训练；用真实高校销量反推合理损耗率 **17.5%**，替代行业基准中不匹配的 5.6%（该修正是回测 MAPE 从 100%+ 降到 6.17% 的关键） |
| ③ `kaggle_food_demand`    | **预训练底座主力**        | 45 万行提供"需求—价格—履约"通用规律，解决高校数据量不足的冷启动问题（迁移学习）                                                      |
| ④ `kaggle_cc0`            | **预训练增量**          | 扩展天气/节假日特征多样性，增强模型对天气敏感性的学习                                                                      |
| ⑤ `reduce_foodwaste`      | **行业基准参考**         | 提供减损率、成本节约的行业对标口径，用于成效报告与答辩佐证                                                                    |

数据流水线：`01_raw（5源）→ 02_processed（清洗+特征工程，可直接建模）→ 03_output（模型+回测报告）→ src/main/resources/modeling（Java 上线产物）`。

## 三、本项目如何训练模型

### 3.1 训练管道（Python，`modeling\scripts\`，可一键复现 `run_all.py`）

```
02_build_pretrain_features.py   预训练特征：③④② 三源拼接，构造滞后/滚动/天气/节假日特征
03_train_pretrain_lgbm.py       预训练 LightGBM（通用需求规律）
04_build_finetune_features.py   高校微调特征：① 2600行 + ② 校准后的 waste_rate=17.5%
05_finetune_and_backtest.py     在预训练基础上微调 + 滚动回测 → 导出高校模型
06_export_for_java.py           导出文本模型 + 24维特征列顺序（供Java加载）
07_validate_kaggle.py           外部验证
08_lstm_baseline.py             LSTM 基线对照（MAPE 8.72%，证明 LGBM 选型）
```

### 3.2 关键技术点

* **迁移学习**：大规模通用数据预训练 → 高校小样本微调，解决冷启动；

* **特征工程（24 维）**：滞后销量（lag\_1/2/3/7）、滚动统计（rolling\_mean\_3/7、rolling\_std\_7）、天气编码、最高温、星期/周末、考试周、校园活动、促销、品类、售价、成本等；

* **log 变换**：对齐不同数据集销量量级；

* **损耗率重估**：用 ② 真实高校销量重估 `waste_rate=17.5%`（原行业基准 5.6% 导致备餐量虚高、MAPE 100%+）；

* **模型形态**：LightGBM 回归，**500 棵树**，目标为 log(销量)。

### 3.3 训练结果（真实回测）

| 模型                | 滚动回测 MAPE  | 说明                            |
| ----------------- | ---------- | ----------------------------- |
| 规则引擎（四因子加权）       | 24.72%     | 系统内置基线                        |
| LSTM 基线           | 8.72%      | 对照实验                          |
| **本项目 LGBM 高校模型** | **3.867%** | 2600 行真实数据滚动回测，较规则提升约 21 个百分点 |

## 四、训练模型 × 智能体：如何嵌入系统联合调度

### 4.1 模型上线：纯 Java 推理（零原生依赖）

训练产物 `lgbm_campus_model.txt` 是 LightGBM 文本格式。服务端 `LgbmCampusModel.java` **不依赖任何原生库**（曾遇 `UnsatisfiedLinkError: no lightgbmlib`，故弃用 JNI 方案），而是纯 Java 解析文本模型：

1. 启动时解析 500 棵树的结构（分裂特征、阈值、左右子节点、叶子值）；
2. 推理时按 `campus_feature_cols.json` 的 24 维顺序构造特征向量，逐树遍历分裂路径累加叶子值，再做 log 逆变换得到销量预测；
3. 上线前已用 Python 原生 LightGBM 对 2600 行全量比对，**两侧预测误差为 0**——线上每一条预测在数学上严格等于训练模型输出。

### 4.2 双引擎预测调度（`DualPredictionService`）

```
用户提交预测请求（菜品/天气/考试周/校园活动）
        │
        ├──► 规则引擎：四因子加权 → 规则预测（兜底，永远可用）
        │
        └──► LGBM 训练模型：24维特征 → 500棵树推理 → 模型预测
                    │
                    └── explain()：逐树路径归因
                        → 每个特征对预测的贡献（份数）+ 命中分裂次数
                        → 高频决策路径规则（如「售价」>11.0 走高值分支）
        │
        ▼
   集成决策：0.6×模型 + 0.4×规则 → 最终备餐建议（首批/补餐/停制时点）
   同时返回：双引擎对比、决策归因、决策规则 → 前端可视化
```

### 4.3 智能体（大模型）联合调度：`ModelCrossCheckService` + `ZhipuAiService`

训练模型负责"算得准"，大模型智能体负责"独立复核与解释"，二者通过 `/api/model/cross-check` 接口联合调度：

```
同一情景的事实包（近7日真实销量、天气、星期、考试周/活动、
                  规则预测、LGBM预测、Top决策因子及贡献）
        │
        ├─① 确定性交叉校验（始终可用，不依赖外部服务）
        │    · 模型运行时就绪（500棵树已加载）
        │    · 回测精度可信（MAPE<10%）
        │    · 训练模型与规则引擎分歧度（>30% 告警）
        │    · 预测是否落在历史合理区间
        │
        └─② 大模型独立混测（配置 ZHIPU_API_KEY 后激活，GLM-4-flash）
             · 要求智能体不迎合任何一方，独立给出预估区间与结论
             · 与训练模型预测比对：一致 / 接近 / 分歧
             · 输出自然语言判断依据，增强可解释性
```

设计要点：

* **决策主权在训练模型**：智能体只做旁路复核，不修改模型输出，保证"决策来自训练"；

* **事实约束**：发给智能体的只有结构化事实，且经营概括类输出有"数字白名单"过滤（只能引用事实中已有的数字），防止大模型编造；

* **优雅降级**：未配置 Key 或调用失败时，自动退回确定性校验，页面功能不受影响。

### 4.4 前端可视化闭环

预测页一次提交即可看到完整证据链：

1. **双引擎对比条**：规则引擎 ＋ 训练模型 LGBM ＝ 最终建议；
2. **训练模型决策依据面板**：8 因子归因条形图（绿=拉高/蓝=压低预测）+ 高频分裂规则原文；
3. **大模型混测面板**：确定性校验结果（如 4/4 通过）+ 智能体独立判断与一致性结论；
4. **需求洞察页**：30 天真实回测序列对比图（实际 vs 规则 vs LGBM）+ Top10 特征重要性。

## 五、线上部署

* 服务器：阿里云轻量应用服务器（2 vCPU / 0.5 GiB / Alibaba Cloud Linux 3），公网 `http://47.254.247.1:8082`；

* 部署方式：Gradle 打包 fat-jar → SFTP 上传 → systemd 服务 `foodwise` 自启动；

* 模型随 jar 打包（`src/main/resources/modeling/`），启动即加载，日志可见 `真实模型加载成功(纯Java推理) trees=500 ... 回测MAPE=3.867%`；

* 大模型能力通过环境变量 `ZHIPU_API_KEY` 注入（不落代码），配置后重启即激活智能体混测。
