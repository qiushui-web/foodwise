# 仿真器实施方案（方案 A 落地版）

**2026-10-27** · 只做规划，不写实现 · 对象：`modeling/scripts/44_simulate.py` 及其配套实验

---

## 1 它要回答什么、不回答什么

**要回答**：在数据很少的情况下，我们这套"区间 + 成本临界比 + 批次约束"的备餐方法，比档口师傅的惯性备餐、比固定安全系数，到底少亏多少？需要多少天才能证明？

**不回答**：任何一个真实档口的减损效果。仿真器产出的所有数字，对外只能写"仿真验证"。

**为什么必须做**：现有 14 天台账跑不出"需要多少天"这类问题——它既没有真值，也没有对照。仿真器提供**已知真值的对照组**，这是唯一能回答样本量、误报率、覆盖率的手段。

## 2 数据契约（第一优先级）

输出 CSV 必须与站点演示台账 `src/main/resources/data/foodwise_operations_14d.csv` **同一 schema、同一单位、同一口径**，这样现有 30–34 号实验脚本可以零改动切换数据源。

| 列名 | 类型 | 生成规则 |
|---|---|---|
| `business_date` | date | 连续营业日（跳过周末可选） |
| `phase` | str | `基线期` / `干预期`（与真实台账一致） |
| `stall` | str | 四个档口：拾味小厨 / 暖食面坊 / 谷禾轻食 / 麦香烘焙 |
| `dish_id` / `dish_name` | int / str | 七个菜品，沿用现有名称 |
| `price` / `unit_cost` | float | 沿用现有 13/5.2、16/7.1、15/6.4、15/6.8、14/6.1、18/8.2、9/3.5 |
| `predicted_qty` | int | 当期决策者给出的预测（惯性决策者=昨日备餐） |
| `prepared_qty` | int | **决策者的实际备餐量**（核心变量） |
| `sold_qty` | int | `min(需求, prepared_qty)`——**必须截断**，这是还原"售罄"的关键 |
| `discount_sold_qty` | int | 收市前折价售出（按折价率折算） |
| `leftover_qty` | int | `prepared_qty − sold_qty − discount_sold_qty` |
| `revenue` | float | `price × sold_qty + price × 折价率 × discount_sold_qty` |
| `weather` | str | 晴 / 阴 / 雨（按校历与季节抽样） |
| `event_tag` | str | 正常教学 / 考试周 / 校园活动 |
| `recommendation_adopted` | bool | 干预期为 true，基线期为 false |

额外加一列 `demand_qty`（**真值**，仅仿真数据有，真实台账没有）。所有评估必须用它算 regret，而不是用 `sold_qty`——否则售罄日会被当成"需求刚好等于备餐"。

## 4 生成模型

**需求层**（每个菜品 d、日期 t）：

```
λ_dt = λ_d × w_weekday(t) × γ_weather(t) × γ_event(t) × (1 + trend × t/30)
demand_dt ~ 负二项(均值 λ_dt, 离散度 k)，并向下截断到 [0, 400]
```

**备餐层**（三种决策者，同一份需求）：

| 决策者 | 规则 | 复现的真实现象 |
|---|---|---|
| **惯性型**（对标现状） | `prepared_t = prepared_{t-1} × (1 + N(0, 0.12))` | 与客流几乎不相关（corr≈0.17）、周一大、周五剩 |
| **安全系数型** | `prepared_t = round(预测 × 1.10)` | 旺日不够、淡日大剩，剩余率随波动放大 |
| **模型型**（本项目） | `q = center + σ·Φ⁻¹(ρ)`，再按最小批次 5、产能 250 取整 | 与站点决策卡完全同一公式，可逐行对照 |

**结果层**：`sold = min(demand, prepared)`；`leftover = prepared − sold − discount`；`regret = c_o·leftover + c_u·max(0, demand − prepared)`。

## 5 校准验收（先定标准，再写代码）

生成 90 天 × 7 菜品后，以下断言必须全部通过，否则参数没调对：

| 断言 | 目标 | 依据 |
|---|---|---|
| 惯性型浪费率 | 14.5% ± 1.5pp | 中国高校堂食 |
| 类别浪费率排序 | 蔬菜 > 米制品 > 豆制品 > 面食 > 牛羊 | 同上 |
| 剩余率分布 | 右偏，中位 < 均值 | 芬兰 KSW |
| corr(备餐量, 客流) 惯性型 | < 0.35 | 芬兰 0.17 |
| 售罄率 | 2%–8% | 真实台账 |
| 模型型浪费率 | < 惯性型，且 > 0 | 方法有效的必要条件 |
| 折价售出 ≤ 剩余 | 恒成立 | 逻辑一致性 |

## 9 风险与红线

1. **仿真自嗨**：只用仿真数据下结论等于自证。必须保留方案 B 的真实数据对照；报告里仿真与真实两节分开写。
2. **参数无出处**：每个参数必须在 §3 表里有来源，没有出处的只能写"情景假设"。
3. **真值泄漏**：`demand_qty` 只用于评估，**绝不能进特征**；测试里加一条"特征列不含 demand_qty"。
4. **误当实测**：文件名带 `sim_` 前缀，CSV 内加 `synthetic` 标记列，报告图题写"仿真器生成"。

## 10 需要你确认的三件事

1. 仿真器是否按"四个档口 × 七个菜品"原样复刻？还是简化成 2 档口 × 4 菜品（更快、但和站点演示不一致）。
2. 星期效应是否跳过周末（食堂周末营业与否）？现在真实台账 14 天是连续营业日。
3. E1 的目标效应量仍按 5pp 吗？如果要按"剩余率从 13% 降到 5%"（真实台账的 7.7pp）来设计，天数会短一些。
