# 35 天现场采集工具包

**2026-10-27 · v1** · 目标：用 35 个营业日，把"方法能不能在真实档口里跑"从推断变成可审计的记录。

## 这个包解决什么

v3 之前的所有数字都来自两处：14 天台账和仿真器。前者样本太小，后者是我们自己造的。真实档口里的三件事还没有证据：

1. 师傅会不会按建议量备餐（**采纳率**）；
2. 按建议量备餐之后，剩余和缺货是不是真的变了（**决策级指标**）；
3. 现场采集的数据本身干不干净（**能不能审计**）。

这三件事都不需要等 35 天才知道答案——但都需要**先写死规则再采**，否则事后怎么解释都行。所以这个包的第一份文件是预注册，不是表格。

## 35 天怎么排

7 周 × 5 个营业日。**按周交替**：一周用系统建议（干预），一周用现行做法（对照），顺序在开跑前用固定种子随机决定并记录在预注册里。

| 周 | 条件 | 要做的事 |
|---|---|---|
| W1 | 随机决定 A/B | 只记录，不改做法（先建立基线记录习惯） |
| W2–W6 | 交替 | 干预周按建议量备餐；对照周按师傅经验 |
| W7 | 随机决定 A/B | 收尾 + 一次全量核对 |

第 1 周无论抽到哪个条件，都先按"只记录、少干预"跑，目的是让当班熟悉表格。**这一周的数据在分析里单独标记**，不能默认进主分析。

## 每天 10 分钟

开餐前（2 分钟）：打开 `/app/prediction`，选菜品与餐次，抄下建议量与区间，填进 `daily_ledger.csv` 的建议量列；干预周就按它备餐，对照周照常。

闭餐后（5 分钟）：填实际准备、售出、折价售出、剩余、缺货时段。**实际准备超出建议量也要如实填**，不许回填成"等于建议"。

收工前（3 分钟）：跑一次校验脚本，红色错误当天修，黄色警告记在 `weekly_review.csv`。

```powershell
cd 项目代码
modeling\.venv\Scripts\python.exe modeling\scripts\48_validate_pilot.py `
  --ledger docs\采集工具包_35天_20261027\data\daily_ledger.csv `
  --output output\pilot-validation.json
```

退出码非 0 表示有阻断性问题，当天不能算完成。

## 哪些是红线

1. **不许改原始记录**。填错了补一行修订，用 `revision_of` 指回原行；不要覆盖。
2. **不许把"没卖完"写成"没做"**。剩余是决策的结果，不是数据错误。
3. **不许把售罄当需求**。售罄当天的销量是下限，不是需求；这类日子在分析里单独标记（`censored=1`）。
4. **不许事后改预注册**。要改就写偏离日志，原文保留。
5. **不许把这份数据说成"已减损"**。35 天、单校、7 周，最多能说"在本校范围内、该设计下、观察到的差异"。

## 与 `docs/pilot/` 的关系

`docs/pilot/` 是更宽的单校试运行与证据包（授权、原件登记、影子运行、用户任务观察）。这个 35 天包是它在**决策实验**这一条线上的收紧版：只采决策需要的最小字段，但把预注册和验收脚本补齐。

两者共用同一套口径：数量单位是份，`prepared = sold + discounted + leftover + waste`，售罄单独标记，不混算。
