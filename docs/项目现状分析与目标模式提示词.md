# 食刻有数：项目现状分析与目标模式提示词

## 一、项目完整定义

### 1. 项目定位

食刻有数（FoodWise）应被定义为：**面向高校食堂档口的低改造成本经营减损与备餐决策 SaaS**。

它不是单纯的可视化大屏、单一销量预测模型，也不是替换食堂 POS 的新收银系统。它的核心角色是在现有食堂经营系统之上增加一层轻量的数据采集、预测、备餐协同、剩余处置和经营复盘能力。

### 2. 核心价值

核心价值应围绕“减少不必要备餐，同时不牺牲售罄和食品安全”展开：

1. 用历史销量、天气、校历、活动和近期经营反馈形成可解释的备餐建议。
2. 把首批备餐、二次补餐、停止制作和剩余处置连接成一个可执行流程。
3. 通过阿姨便捷录入、POS/刷卡数据导入和人工修正，持续获得真实经营数据。
4. 用限时优惠、订单核销和安全护栏处理可售剩余，形成减损闭环。
5. 用经营复盘、预测误差和风险预警帮助档口形成可追溯的改进依据。

### 3. 核心业务闭环

```text
经营数据采集
  -> 需求预测
  -> 分批备餐建议
  -> 餐次经营与剩余登记
  -> 安全护栏下的限时优惠
  -> 订单核销
  -> 经营复盘与人工反馈
  -> 下一周期模型与规则修正
```

### 4. 目标用户

- 档口工作人员：需要极低学习成本、少打字、单屏完成餐次录入。
- 食堂管理员：需要查看档口经营、异常风险、数据质量和减损结果。
- 学校/团餐运营方：需要评估试点价值、投入成本、跨档口复制性和审计能力。
- 交付与技术团队：需要稳定 API、可回滚模型、可复现数据流水线和清晰的权限边界。

## 二、现状判断

### 1. 已确认事实

- 当前同时存在 Vue 3 + TypeScript + Element Plus + ECharts 前端，以及 Spring Boot + Spring JDBC + Spring Security 后端。
- 后端已包含规则预测、LightGBM 纯 Java 推理、双引擎预测、模型交叉校验、经营反馈、优惠和核销等能力。
- 项目目录同时保留 Thymeleaf 页面和 Vue 应用，存在两套前端入口，必须明确主入口。
- 现有前端已覆盖经营驾驶舱、档口与菜品、备餐决策、限时优惠、订单核销、经营回传、复盘、预警和洞察页面。
- 数据目录包含高校食堂浪费数据、校园交易数据、通用食品需求数据、零售天气数据和减损基准数据，并保留 Python 建模脚本与 Java 模型产物。
- 当前前端视觉已朝“简易、自然、高级”的运营台账方向调整，后续应以一致性和可用性为主，不再增加无业务价值的装饰。

### 2. 必须承认的口径冲突

项目材料存在以下尚未完全统一的问题，任何对外数字必须先标注来源、数据范围和指标定义：

- `modeling/data/README.md` 记录 98 条团队实地经营台账；其他说明记录 2,600 行高校浪费数据。
- `campus_backtest_report.json` 记录 LGBM MAPE 3.867%、规则基线 22.547%；`MODEL_CARD.md` 记录 LGBM MAPE 6.166%、规则基线 24.7245%。
- 文档一处写“全真实、零模拟”，另一处又把 SmartBite 合成数据作为预训练底座。
- README、项目说明和实际代码存在不同技术栈与入口描述，不能把文档描述直接当成当前运行事实。

在口径统一前，只能使用“已核验的当前构建/接口结果”作为产品展示结论；未经统一的指标必须显示为“实验记录”或“待核验”，不得在首页写成确定性商业承诺。

### 3. 现有技术约束

- 主技术栈固定为 Vue 3 + Element Plus + ECharts + Spring Boot；除非已有接口无法满足且经过评估，不新增 FastAPI 服务。
- Java 17、H2 开发环境、MySQL 生产环境和 `/api/v1` 接口前缀属于现有兼容边界。
- Java 端模型推理必须保持与 Python 导出模型的特征顺序、变换方式和预测结果一致。
- 大模型只允许做旁路复核和解释，不能替代训练模型、修改最终备餐结果或生成无事实依据的经营数字。
- 前端必须保留加载、空数据、错误、权限和降级状态，不能用静态假数据掩盖 API 失败。
- 任何新指标都必须能追溯到数据库字段、接口响应、模型产物或明确的计算公式。

### 4. 当前风险

**P0：无法稳定验收的运行风险**

- `ApiV1Controller` 存在若干 `ApiResponse.success("...")` 泛型返回错误，导致 Spring Boot 无法编译或启动。
- Vue 前端与后端未完成稳定联调时，页面可能出现空白，不能把空白页面误判为视觉问题。

**P1：产品可信度风险**

- 两套前端入口并存，用户可能访问到不同版本。
- 数据集、样本量、回测窗口和 MAPE 数字不统一，答辩或客户演示时容易被追问。
- 当前产品更像“功能集合”，需要进一步强化从预测到实际经营改善的主线。

**P1：业务落地风险**

- POS、刷卡、OCR、语音和小程序方案很多，但多数仍是方案描述，不应在界面上伪装成已交付能力。
- 多档口、多校区、权限隔离、数据审计和数据授权仍未形成完整产品边界。

**P2：模型与数据风险**

- 多源数据拼接的地域、时间、业务口径差异可能影响迁移泛化。
- 回测结果需要固定数据版本、滚动窗口、指标定义和基线实现后才能对外引用。
- 经营台账录入质量、缺失值、重复导入和人工修正会直接影响模型反馈闭环。

## 三、分优先级优化方向

### P0：先恢复可运行、可验证、可解释

1. 修复后端控制器泛型错误，保证 `gradlew build` 和 `bootRun` 可执行。
2. 明确唯一主入口：Vue 3 应用作为主产品入口；Thymeleaf 页面保留为兼容或迁移参考，并在文档中标记状态。
3. 建立 API 契约清单：请求字段、响应结构、错误码、空状态和权限要求与前端类型逐项对齐。
4. 所有首页 KPI、图表和模型指标增加“数据时间范围/来源/计算口径”入口，失败时显示可理解的降级状态。
5. 以真实 API 数据完成桌面、移动端和至少一条完整业务链路的浏览器验证。

潜在影响：短期会暴露更多接口和数据问题，但能消除“页面看起来完成、系统实际不可运行”的最大风险。

### P1：围绕一条主线重组产品体验

1. 将导航和首页叙事统一为：今日经营总览 → 明日备餐 → 餐中调整 → 剩余处置 → 经营复盘。
2. 驾驶舱只保留决策所需指标：今日销量、预计剩余、备餐风险、待处理预警、待核销优惠和数据新鲜度。
3. 预测页面优先展示“建议做什么、为什么、风险是什么”，再展示模型细节；双引擎差异、特征归因和交叉校验作为证据层。
4. 为档口工作人员设计“大按钮、少输入、可复制昨日、弱网可恢复”的独立录入流程，不把管理员后台直接缩小给一线人员使用。
5. 将优惠活动、食品安全时段、核销和过期下架设计成一个完整状态机，而不是孤立 CRUD 页面。

潜在影响：会减少部分装饰性页面和重复入口，但能明显提高演示可理解性和真实使用效率。

### P1：建立可信的数据与模型治理层

1. 建立数据源登记表：来源、许可、样本量、时间范围、地域、字段、用途和是否可对外引用。
2. 统一回测报告版本，明确 3.867% 与 6.166% 各自对应的数据、窗口和脚本；在统一前不要并列宣传。
3. 将“公开真实数据”“团队实测数据”“合成/预训练数据”“示例演示数据”分层标记。
4. 记录模型版本、特征版本、训练时间、随机种子、滚动窗口、基线和资源消耗。
5. 对人工反馈、异常修正、重复导入和数据缺失提供审计记录。

潜在影响：需要补充元数据和界面标识，短期增加治理工作，但会显著降低答辩、试点和商业交付中的可信度风险。

### P2：从演示产品走向可复制交付

1. 实现角色权限、档口/校区数据隔离和操作审计。
2. 优先落地 POS CSV/Excel 导入和刷卡流水聚合，OCR、语音和硬件联动作为可插拔适配器。
3. 完成优惠二维码、定时下架、核销异常处理和报告导出。
4. 建立多租户配置、模型服务独立扩展和消息订阅等商业化能力。

潜在影响：会引入更复杂的权限、部署和运维成本，应在 P0/P1 稳定后再推进。

## 四、目标模式提示词（可直接复制使用）

```text
你现在负责优化“食刻有数（FoodWise）”项目。请把它视为一个面向高校食堂档口的低改造成本经营减损与备餐决策 SaaS，而不是普通数据大屏、单一预测模型或新的 POS 系统。

【目标】
在不破坏现有业务逻辑和数据可追溯性的前提下，统一产品定位、前后端入口、视觉语言和接口契约，形成“经营数据采集 → 需求预测 → 分批备餐 → 剩余登记 → 安全优惠 → 订单核销 → 经营复盘 → 反馈学习”的可运行闭环。

【固定技术边界】
- 前端：Vue 3 + TypeScript + Element Plus + ECharts + Pinia + Vue Router。
- 后端：Java 17 + Spring Boot + Spring JDBC + Spring Security。
- 数据库：开发使用 H2，生产兼容 MySQL 8。
- API 前缀：/api/v1。
- 模型：Python 训练、Java 纯推理；保持特征顺序、变换、模型版本和结果一致。
- FastAPI 不是默认新增项。只有在现有 Spring Boot 无法合理承载且给出接口、部署、监控和回滚方案时才引入。

【执行顺序】
1. 先读取仓库说明、依赖、数据库 schema、API 控制器、前端路由、状态管理、模型卡、回测报告和运行日志。
2. 先输出“事实/推断/待核验”三栏审计，不要把文档宣称直接当作运行事实。
3. 先修复构建、启动和 API 契约问题，再做业务行为调整，最后做视觉优化。
4. 每次修改保持小步、可回滚，并说明影响的页面、接口和数据口径。
5. 用真实 API 完成桌面和移动端浏览器验证；不能用静态假数据掩盖接口失败。

【产品体验原则】
- 视觉：简易、自然、高级；采用克制的运营台账风格、清晰层级、低噪声配色和稳定密度。
- 首页：只回答“今天发生了什么、明天该做什么、现在需要处理什么”。
- 预测：先给行动建议，再给原因、风险和模型证据。
- 档口录入：大按钮、少输入、可复制昨日、弱网可恢复、适合戴手套操作。
- 优惠：必须展示安全时段、库存、折扣护栏、状态和核销结果。
- 所有页面都要有加载、空数据、错误、权限和降级状态。

【数据与指标规则】
- 所有 KPI、图表和模型指标必须标注来源、时间范围、单位和计算口径。
- 未统一的数据集规模、回测窗口和 MAPE 不得写成确定性宣传结论。
- 区分公开真实数据、团队实测数据、合成/预训练数据和演示数据。
- 大模型只能旁路复核和解释，不能修改训练模型的最终备餐结果，也不能编造事实数字。

【业务边界】
- 当前版本重点是经营数据、备餐决策、剩余处置、核销和复盘。
- POS/刷卡导入优先支持 CSV/Excel；OCR、语音、硬件和小程序作为后续适配能力，不得伪装成已完成能力。
- 多校区、多租户、支付、消息订阅和完整硬件生态属于后续商业化阶段。

【必须交付】
1. 项目现状审计：定位、核心价值、用户、边界、约束、风险和优先级。
2. 变更清单：文件、接口、页面、数据口径和潜在影响。
3. 可运行实现：构建成功、后端可启动、前端能加载真实 API。
4. 验证记录：构建命令、测试结果、桌面/移动端浏览器检查、控制台和接口错误。
5. 剩余风险：明确哪些仍是方案、哪些指标待核验、哪些能力未实现。

【禁止事项】
- 不新增未经验证的业务数字、用户数量、节省金额或模型精度。
- 不为了视觉效果删除错误、空状态、权限、隐私、许可或数据来源信息。
- 不同时维护两套“主产品”而不说明入口优先级。
- 不在未验证时宣称后端联调、模型效果或商业化能力已经完成。
```

## 五、建议的验收标准

- `frontend` 可以稳定执行 `npm run build`。
- 根目录可以稳定执行 `gradlew build`，并能在默认开发配置下启动。
- `/api/v1/health`、驾驶舱、预测、优惠、订单和反馈接口与前端类型一致。
- 首页和预测页在 API 成功、空数据、接口失败三种状态下都可理解。
- 桌面与移动端主流程无明显溢出、遮挡或不可点击区域。
- 所有对外展示指标都能追溯到来源文件、接口或公式。
- 最终交付不包含个人绝对路径、调试残留、未处理 TODO 或伪造的完成状态。
