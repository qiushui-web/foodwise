# 食刻有数 · 网站内容与定位识别报告

> **识别对象**：`项目代码/` 内 Spring Boot + Vue 单体的站点（本地实例 `http://localhost:8089`，生产前缀 `/foodwise/`）。
> **识别时间**：2026-10-27 08:24–08:45（Asia/Shanghai）。
> **识别方法**：源码静态盘点（路由、视图、组件、样式、模板、控制器、前端 API 调用）+ 本地实跑（`gradlew bootRun`，local/H2）+ 真实浏览器逐页取证（Playwright，1440×960 全页截图 15 张、390×844 移动端 2 张、控制台错误监听）+ 文档交叉核对（README、`docs/`、计划书主稿 1.1–1.5/2/6/7/10 章、`项目全景与计划书维护手册.md`）。
> **证据分级**：**【实测】**＝本次直接读取或运行得到；**【文档】**＝项目内既有文档记载、本次未复现；**【待核】**＝未验证，不得当作结论。
> **一句话结论**：这是一个**只对食堂内部开放的“单档口经营工作台”**，不是品牌官网；它的真实定位不是“AI 减损平台”，而是**把台账变成可人工复核的备餐建议、再把执行结果记回台账的证据链工具**，站内每一页都在用“未验证/不代表/待核验”给自己的主张降级。

## 0. 一分钟结论

1. **站点规模**【实测】：15 条路由（13 个业务页 + 登录 + 404），全部返回 200，全站无 JS 控制台错误；可见正文约 **4,200 字**，最重的两页是“经营复盘报告”（1,369 字，其中约 430 字是未翻译英文限制，约三成）与“服务说明”（868 字）。
2. **站点性质**【实测】：唯一的品牌叙事页是登录页；未启用安全策略时 `/` 会直接进入演示工作台，启用后先落登录页。全站**没有**价格、套餐、案例、联系方式、公司介绍、学生端下单入口——对外品牌与商业叙事不在网站上，只在计划书/PPT 里。
3. **真实用户**【实测】：高校食堂档口经营者（首要）、食堂运营方/后勤（准入与管理）、平台三种账号（ADMIN/OPERATOR/ANALYST）。学生只以“优惠与核销的隐含对象”出现在文案中，网站没有学生侧界面。
4. **信息架构**【实测】：主导航被收敛成五步——建档与菜品 → 录台账 → 做备餐计划 → 处理剩余 → 看复盘；档口、预警、三个分析子页退为弱入口（分析页仅“服务说明”底部可点）。
5. **定位特征**【实测】：全站最鲜明的不是“AI”，而是**证据克制**——16 处独立边界声明（“演示环境 · 非实时经营数据”“经验范围尚未校准”“不代表现场减损收益”等），且全站 0 次出现“AI/智能/算法”字样，只说“规则模型”“LightGBM”。
6. **定位错位**【实测+文档】：外部口径（AGENTS.md、计划书摘要、PPT 副标题）是“AI 辅助备餐与经营减损服务”，站内实际是“规则引擎 + 台账流程 + 保守声明”；文档里的 6.17%/24.72% MAPE 已被 `MODEL_CARD.md` 与网站现行公开实验推翻，属**文档比网站更乐观**的倒挂。
7. **定位判定**：产品处于 **“可演示、可本地验收、待授权试点”** 阶段（单校原型，TRL 5–6）；网站承担的是**作业界面**职责，不是增长与转化页面。

## 2. 全站信息架构

### 2.1 三层结构【实测】

```
登录页（唯一对外门面）
  └─ /app 工作台（AppLayout：左侧五步导航 + 顶栏）
       ① 建档与菜品  /app/onboarding（ADMIN 可见）
       ② 录台账      /app/operations/feedback
       ③ 做备餐计划  /app/prediction
       ④ 处理剩余    /app/offers → /app/orders（核销）→ 回台账回填
       ⑤ 看复盘      /app/reports
     顶栏：总览 · 待处理预警（有数量才出现）· 使用说明

     兜底：404「页面未找到」
```

### 2.3 结构层判断

- **导航是“按任务”而非“按功能”**：五步即一条营业日闭环，评审看导航就能复述业务流程——这是当前 IA 最大的优点。
- **弱入口是刻意的**：分析页、档口页、预警页不进主导航，避免普通运营者被指标墙淹没；代价是**评委按“功能齐全度”点检时会找不到**，需要口头引导或补一条入口说明。
- **档口页与建档页职责重叠**：都涉及菜品命名与编号，一处是“建立”，一处是“核对”，文案已作区分，但入口位置让前者看起来像主流程。

## 3. 逐页内容清单

> 记法：**任务**＝这一页唯一的主动作；**模块**＝首屏可见区块；**边界**＝页面自己写的免责/限制句。

### 3.1 登录页 `/login`

- **任务**：以运营账号进入工作台。
- **结构**：左品牌区（Logo + 主标语 + 副标语 + 一句能力描述）+ 右登录卡（OPERATION PORTAL / 进入经营工作台 / 账号密码 / 登录按钮 / 小字说明）。
- **原文**：“让每一份备餐**更有依据**”“高校餐饮精细化经营与食品减损服务”“统一管理经营台账、备餐建议、限时优惠、订单核销和经营复盘。”“账号由食堂运营方统一配置”。
- **边界**：“请使用运营账号登录”；失败态“账号或密码不正确”。
- **判断**：这是全站唯一的品牌叙事页，一句话讲清了“凭什么”——**依据**。但它只服务已有账号的人，对外没有说服材料（无案例、无数字、无资质）。

### 3.2 经营总览 `/app/dashboard`

- **任务**：确认“最近一个有记录的营业日”发生了什么，然后去下一步。
- **模块**：① 三指标条（实际备餐 383 份 / 实际售出 364 份·占 95% / 当前记录剩余 19 份·优惠售出 10 份）② “近期备餐与售出”柱状图（售出/未售出双色，单位份，仅显示有记录营业日）③ “接下来”待办卡（3 条预警、5 笔待核销、台账）④ 折叠“数据范围与使用说明”。
- **边界**：顶栏“演示环境 · 非实时经营数据”；“经营趋势为演示快照；备餐前请先录入自己的历史台账”；“营业中的盘点可能尚未反映闭餐结果；以上数字不能直接解释为已验证的减损成效”。
- **出口**：先录入台账 / 制定备餐计划（按是否有台账切换）、预警、订单、复盘。
- **判断**：标题“从最近营业日，走向下一步”把“看数”降级为“做动作”，与产品定位一致；三指标比早期的四宫格更克制。

### 3.3 首次建档 `/app/onboarding`

- **任务**：把学校、档口、首个菜品的数据口径立住。
- **模块**：四段表单（学校与数据授权：授权材料引用/用途/保存期限；档口信息；首个菜品：售价、单位成本、备餐分钟、计量单位；操作责任）+ 右侧粘性“准入检查”清单（就绪/仍需补充）。
- **原文**：“先建档，再生成备餐建议”“提交后仍需人工核验授权和原始台账，建档状态不会自动等同于已授权”“首版只接受‘份’，避免把碗、个、克等不同口径混入同一条训练序列”。
- **判断**：把“合规与单位口径”做成表单字段，而不是写在附录里——这是本项目最像“真实业务系统”的一页，也是竞品 demo 通常缺失的一页。

### 3.4 档口与菜品 `/app/stalls`

- **任务**：核对菜品名称、价格与编号（CSV 导入要用 dish_id）。
- **模块**：4 张档口卡（拾味小厨 / 谷禾轻食 / 暖食面坊 / 麦香烘焙：菜品数、评分、最近营业日收入）+ 三图菜品画廊“从菜品认识档口”+ “成本与历史表现”表（菜品 ID、菜品、档口、售价、单位成本、平均销量、剩余率）。
- **边界**：“图片为同类菜品实拍示意，不代表档口当日出品。”
- **判断**：菜品照片是“同类示意”，页面反复标注——诚实，但也说明**产品没有真实出品影像资产**，视觉真实感靠外来图。

### 3.5 备餐计划 `/app/prediction`

- **任务**：确定“下一餐备多少”，先分批，再确认执行。
- **模块**：左输入条件（菜品、天气、目标营业日、餐次、考试周、校园活动）+ 菜品缩略图；右结果区（空态“等待生成建议”）→ 生成后：经验参考范围、先制作/视销售补餐/停做时间、分批构成条、售罄/剩余风险、建议摘要、折叠“查看数据范围与计算依据”、**现场执行层**（库存/产能/最小批量/提前期/三段时段 → 生成并留档备餐计划 → 计划编号与缺口）、“核对本次预测输入”、执行计划确认表单（采用/自定、总备餐量、原因）、“关联本次建议，回填经营结果 →”。
- **边界**：“经验范围尚未完成区间校准，不代表准确率或覆盖概率”“只做参考，不自动扣库存”“预测数量和停做时间是辅助建议，不能替代现场判断与食品安全确认”“历史台账距目标日已超过 14 天”强提示。
- **判断**：全站信息密度最高的一页，也是“创新点”真正落地的地方：预测 → 现场约束 → 留档 → 人工确认 → 回填，五段全部有 UI，且每段都能被驳回（原因必填）。

### 3.6 经营数据回传 `/app/operations/feedback`

- **任务**：把当餐盘点/最终结果记进台账（单条或 CSV 批量）。
- **模块**：双 Tab；单条录入 11 个字段（日期、餐次、菜品、建议/实际/售出/剩余/优惠售出/收入、天气、操作人 + 事件标签、备注）+ 数量守恒提示 + 预测关联块 + 食品安全勾选；右侧“这餐的份数去向”实时核对（已售/剩余比例条、差额提示）；CSV 预览与导入（含来源声明四项：来源名称、提供方、地域范围、授权引用）；“最近经营记录”表（可“继续填写”）；“最近来源登记”（含 SHA-256）。
- **边界**：“校验关系：实际备餐 = 实际售出 + 当前剩余”“优惠售出已经计入实际售出，不要重复相加”“填写声明不等于来源和授权已经核实”“登记保存文件指纹…逐项核验后再用于真实校园训练”。
- **判断**：这是全站“证据感”最强的一页：数量守恒、来源指纹、授权引用、改写留痕。它比预测页更能解释“为什么这不是一个 AI 玩具”。

### 3.7 限时优惠 `/app/offers`

- **任务**：把可售剩余转成安全时段内的优惠。
- **模块**：四步流程条（01 记录当餐盘点 → **02 核对并发布** → 03 核销订单 → 04 回填最终结果）；选菜品 → 生成建议（份数、价格、折扣、建议时段）→ 勾选“已核对实物状态、库存及食品安全售卖时间”→ 发布；已发布活动清单。
- **边界**：“优惠建议不会自动代替现场判断”“默认时间仅为经验参考…截止时间须晚于当前时间”“只有已有订单才能在订单页核销”。
- **判断**：把“促销”明确降级为“剩余处置”，与“不做流量/会员”的定位一致。

### 3.8 订单核销 `/app/orders`

- **任务**：窗口交付后核销。
- **模块**：6 位取餐码查询 → 订单卡（菜品、份数、取餐点、金额、订单号、状态）→ “餐品已交付，确认核销”；“近期待取餐 5 笔”队列。
- **边界**：“只核销系统中已有的订单”（服务说明页）。
- **判断**：功能完整但**没有下单方**——订单来自演示数据，站内没有任何学生下单/预约界面。

### 3.9 经营预警中心 `/app/alerts`

- **任务**：处理影响当班的预警。
- **模块**：预警列表（级别、类型、营业日、菜品、档口、原因文案，例：“闭餐剩余4份，建议复核下一餐首批备餐量”）+ “核对该菜经营记录 →” + “现场处理后标记”。
- **边界**：“先查看预警原因，完成现场处理后再标记‘已处理’。”
- **判断**：预警文案是可执行的一句话，不是指标报警，符合“动作导向”。

### 3.10 经营复盘报告 `/app/reports`

- **任务**：把“建议—计划—实际”的差异算清楚。
- **模块**：① 台账汇总（基线期 vs 策略期剩余率同刻度对比、“两图同一刻度：0–15%”、建议执行率、剩余成本测算差额）② 逐次复盘（最近 100 次预测按菜品/日期/餐次匹配；建议量 vs 实际售出条形对比 + 五列表格：预测/确认计划、售出/制作、预测/执行偏差、调整原因/记录来源/历史截止）③ 折叠“公开数据实验与验证范围”（数据集、单位、模型、run_id、测试样本、LightGBM MAE vs 同星期均值基线 MAE）。
- **边界**：“可能包含尚未闭餐的盘点；不能视为已实现的现场减损或因果收益”“两阶段剩余率相差 x 个百分点——描述性测算对照，不能证明由系统造成”“当前 LightGBM MAE 高于同星期均值基线。这组实验不能解释为份数、人民币、产能或现场减损收益”，另附 5 条英文限制（观测销量截断、缩放销量不可换算、无货币换算、无跨数据集泛化、非对称损失不含产能与成本）。
- **判断**：**全站可信度最高、也最“不好看”的一页**：它公开承认模型不如基线。对竞赛是加分（诚实），对商业演示是减分（无胜绩），这页的取舍本身就是定位表态。

### 3.11 三个分析子页 `/app/insights/{realtime,demand,waste}`

- **共同结构**：页头（经营分析 + 标题 + 描述）→ 来源说明行（营业日期 + “项目经营台账；演示测算与公开验证分别阅读”）→ 4 指标（备餐/售出/剩余 + 模式专属第 4 格：售罄率 / 测试样本数 / 优惠挽回）→ 主面板（LIVE SNAPSHOT 经营健康度条形 / MODEL BACKTEST 观测-基线-LightGBM 对照表 / WASTE CONTROL 餐品流向条形）+ 右栏 RISK SNAPSHOT“需要关注的菜品”。
- **边界**：“不代表实时监测”“缩放销量可能为负数，不可换算份数”“不代表现场减损收益”。
- **判断**：三页共用一个组件、只换文案与一格指标，**内容增量很小**；命名与内容存在自相矛盾（见 §6.1），是定位表达最薄弱的一环。

### 3.12 服务说明 `/app/about`

- **任务**：教第一次用的人跑完一轮，并交代边界。
- **模块**：使用前准备（4 条）+ 按餐次四步（01 先录历史数据 → 02 营业前生成计划 → 03 盘点后处理剩余 → 04 更新结果并复盘，每步带跳转）+ 继续查看数据（三个分析页链接）+ 关键数据怎么填（实际备餐/实际售出/优惠售出/当前剩余四个定义 + 校验式）+ 使用边界 + 菜品图片来源（7 张 Wikimedia 图逐张署名与许可）。
- **边界**：“当前不会自动从 POS、刷卡机或学生端读取销售数据；经营人员仍需主动录入或导入台账”“订单页只核销系统中已有的订单”“复盘汇总…不能直接视作最终减损成效”。
- **判断**：这一页承担了“产品说明书 + 合规声明 + 图片来源”三重职责，是评委最可能逐字读的页面；图片版权链完整。

### 3.13 404 `/app/*`

- **内容**：“未找到这个页面”“地址可能已变更，请从导航重新选择。”+ 返回经营总览。
- **问题**：返回 **HTTP 200**（软 404），对搜索引擎与外部链接检查不友好【实测】。

### 6.4 差异化与非目标（站内可见）

**差异化**：① 从人工/CSV 起步，不要求先上硬件；② 决策绑定“营业日 × 餐次 × 档口 × 菜品 × 份数”；③ 预测—计划—回填三段留痕，偏差可归因；④ 来源登记 + 授权引用 + 数量守恒，把合规做进流程。

**非目标（页面与文档一致）**：不替代智慧食堂硬件、POS、采购、食品安全监管、校园支付；不做连锁运营、流量、会员；不做跨校实时接入；不宣称发明算法；不把演示数据当现场成效。
